# nc-interview 部署文档

> 面经学习网站的完整部署方案。截至 2026-09-13。
>
> **一句话**：Go + MySQL + 原生前端的单二进制应用，配一条「抓取 → 入库 → 规则归类 → 模型归类」的数据管线。无框架、无 CGO、无构建步骤。

---

## 一、这是什么

把牛客上公开的面试经验（面经）抓下来，清洗归类成**可复习的知识点**，用网页多维检索。

当前数据：全站抓取进行中。已入库 464 篇面经 / 70 家公司 / 3859 组问题（4132 条出现记录），
其中 672 组带参考答案（来自牛客官方结构化真题）。

### 三层数据模型

```
posts（原始帖子，带原文 URL）
   │
occurrences（问题 × 帖子的出现记录，携带该帖里的原始措辞）← 核心
   │
questions（去重后的问题）
```

**`occurrences` 是整套设计的支点**：它同时连接两端，所以每个问题都能回答
「谁、什么时候、哪场面试里问的」，并直接给出**原文链接**（`/feed/main/detail/<uuid>`）。

**频次在筛选范围内重算**，不是全库计数——「一面 + Agent/AI」下的 `n` 只统计符合条件的
出现记录（`JOIN` 之后 `GROUP BY q.id`）。这是「按维度看高频题」能成立的前提。

### 两套分类并存（刻意）

| | 规则分类 | 模型分类 |
|---|---|---|
| 实现 | 正则优先级 | LLM（子代理分批） |
| 粒度 | 7 模块 / 23 主题 | 26 可用类 / 6 域 / 50 细分类 |
| 优点 | 毫秒级、离线可重跑、可解释 | 语义准确、能识别非题目 |
| 缺点 | 换个说法就散 | 需调模型、有成本 |

### 六个可筛选维度

> **「按模块」页的二级下钻用 LLM 细分类，不用规则主题。**
> 实测规则主题在这一页已经失效：「后端工程」模块下 **75% 的题落进「其他技术」**，
> 下钻等于没下钻。换成 LLM 细分类后，同一批题呈现为 83 个知识点、
> 最高的一档只占 8%（项目经历深挖 487 / 编程语言特性 474 / 数据库与 SQL 360…）。
> 接口是 `GET /api/llmcats?category=<模块>`。


轮次 / 岗位 / 公司 / 规则模块 / 规则主题 / **LLM 知识点（三级下钻）**

## 三、从零部署

### 步骤 1：建库建用户

```bash
mysql -u root -p < scripts/setup.sql
```

`setup.sql` 会创建：
- 数据库 `nc_interview`（`utf8mb4_unicode_ci`）
- 用户 `nc_app`（**只对 `nc_interview` 有权限**，最小授权）

⚠️ **密码策略坑**：Homebrew 的 MySQL 默认启用 `validate_password`（MEDIUM），要求
**长度≥8 + 大写 + 小写 + 数字 + 特殊字符**，且不能含用户名。纯随机字母数字即使 24 位也会被
`ERROR 1819` 拒绝。

DSN 里的密码建议只用这些特殊字符（避开 shell 与 DSN 转义问题）：

```
%  *  +  -  =  ^  _
```

（`@` 会干扰 DSN 的凭据/地址切分，`!` 在交互式 shell 里触发历史展开。）

### 步骤 2：配置连接

```bash
cp .env.example .env
vi .env     # 填 NC_DB_PASS
```

`.env` 已在 `.gitignore` 中，不会被提交。环境变量优先于 `.env`。

| 变量 | 默认 | 说明 |
|---|---|---|
| `NC_DB_USER` | `nc_app` | 数据库用户 |
| `NC_DB_PASS` | — | **必填** |
| `NC_DB_HOST` | `127.0.0.1:3306` | |
| `NC_DB_NAME` | `nc_interview` | |
| `NC_DSN` | — | 完整 DSN，设了就覆盖上面四项 |
| `NC_ADDR` | `127.0.0.1:8787` | 监听地址 |
| `NC_WEB` | `web` | 前端目录 |
| `NC_USER_ID` | `125006155` | 目标牛客用户 |
| `NC_COOKIE` | — | 仅在线抓取需要（当前公开内容免 Cookie 即可） |

启动日志会打印**脱敏 DSN**（`nc_app:****@tcp(...)`），密码不进日志。

### 步骤 3：建表 + 导入数据

```bash
make import     # 从 data/posts.jsonl 导入；首次运行会自动应用 migration 建表
make run        # → http://127.0.0.1:8787
```

### 步骤 4：LLM 归类（可选但推荐）

```bash
make llm-apply  # 导入 data/llm/ 下已有的模型归类结果
```

## 四、常用命令

```bash
make help        # 列出全部
make build       # 编译 4 个二进制：bin/nc（服务）、nc-scrape、nc-fetch、nc-parse
make run         # 启动服务
make scrape      # 在线抓个人时间线（需 NC_COOKIE）
make import      # 从 data/posts.jsonl 导入
make rebuild     # 用库内帖子重建规则聚类（LLM 标注会按 norm 自动保留）
make llm-apply   # 导入 LLM 归类结果
make llm-stats   # 分析 LLM 归类，输出合并决策依据
make test        # 单元测试
make check       # 格式化 + 检查 + 测试 + 编译

# —— 全站面经：抓取 ——
make fetch-dry   # 只看本次会抓哪些 URL，不发请求
make fetch       # 抓 500 条（随机 1.5~4s + 每 30 条长休息，Ctrl-C 可中断续抓）
make fetch-check # 复核已抓数据，删掉空壳页并让它们重新排队

# —— 全站面经：入库 ——
make parse-dry   # 试解析，只统计不写库
make parse-only  # 只解析入库，不重建聚类
make parse       # 解析入库 + 重建聚类 + 清理空帖（-classify -prune）
```

## 五、数据管线

### 5.1 抓取

两种模式，**都遵守 robots.txt**（该站仅禁 `/search`、`/nccommon`、`/ab/`）：

**A. 个人动态列表**（`make scrape`）——需要登录 Cookie

```
GET https://gw-c.nowcoder.com/api/sparta/user/content/my-content?pageNo=N&userId=X
```

注意两个易错点：主机是 **`gw-c`** 而不是 `www`；参数是 **`pageNo`** 而不是 `page`。
拼错会返回 SPA 的 HTML 外壳（HTTP 200 但不是 JSON），非常容易误判。

响应里**直接带完整正文**（`records[].momentData.content`），无需逐篇抓详情页。

**B. 全站公开内容**（`make fetch`）——**免登录**

`sitemap1.txt` + `sitemap2.txt` 共 **26,623 条**已发布 URL（16,163 条 `/feed/` + 9,856 条 `/discuss/`），
这是牛客**主动发布给爬虫**的入口（`robots.txt` 声明），抓它不越界。

```bash
make fetch-dry                  # 先看队列，不发请求
make fetch                      # 默认 500 条
go run ./cmd/fetch -limit 2000 -type feed -min 2s -max 5s
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-limit` | 500 | 本次最多抓多少条（已抓过的不计入） |
| `-min` / `-max` | 1.5s / 4s | 请求间隔，在区间内**均匀随机** |
| `-long-every` | 30 | 每 N 次请求插入一段长休息（`0` 关闭） |
| `-long-min` / `-long-max` | 12s / 40s | 长休息时长区间 |
| `-tries` | 3 | 单条 URL 的就地重试次数 |
| `-shuffle` | true | 打乱顺序，避免每次重跑都从同一段前缀开始 |
| `-type` | all | `feed` / `discuss` / `all` |
| `-dry` | | 只列 URL |
| `-recheck` | | 复核已抓数据并退出 |

**为什么随机频率 + 长休息**：固定间隔是最容易被识别的爬虫特征。
实测固定 0.5s 连发时约 **2/3 的请求会拿到空壳页**；改成随机 1.5~4s 并加长休息后降到 **0**。

**落盘**：原始响应 gzip 存 `data/raw/<sha1(url)[:20]>.html.gz`，索引追加在 `data/raw/_manifest.jsonl`。
按 URL 哈希判定「已抓」，所以**重跑自动续抓**、可随时 Ctrl-C。
解析规则会变，原始数据不该因此重抓——这是抓取与解析分离的全部理由。

#### 空壳页：200 不等于拿到内容

牛客会间歇性返回约 **6KB 的骨架 HTML**（只有 `<head>`，没有 SSR 数据），
**同一个 URL 隔几秒重试就恢复正常**（实测 6KB → 158KB）。这是瞬时降级，不是链接失效。

侧信道验证过：抓取器在跑的时候，另开一个全新会话（无 Cookie）请求同样拿到空壳页，
说明这是**站点级的软限流**，不是本地会话被烧。

处理方式（三道）：

1. **抓取阶段识别**：`LooksLikeContentPage` 检查正文是否含 `contentData`；
   不含则 `Get` 按**可重试失败**处理（退避后重试），**不落盘**。
2. **就地重试**：`-tries 3`，每条 URL 内部重试，失败则留在队列里下一轮再来。
3. **事后复核**：`make fetch-check` 扫描已落盘数据，删掉空壳并重写清单，
   被删的 URL 自动重新排队。用于清理「识别逻辑上线之前」落下的脏数据。

#### `createdAt` 可能是 null

从旧站迁入的老帖（`/discuss/<数字ID>` 那批）`createdAt` 是 `null`，只有 `editTime`。
代码用 `editTime` 兜底：它是「最后编辑时间」，**只会偏晚不会偏早**，
对「近 N 个月」这类过滤是可接受的近似，总好过把日期落成 1970。

#### 打卡动态是最大的噪声源

约 20% 的抓取结果 `content` 为空——它们是**打卡动态**（`clockMoment` 有值、`circle` 是打卡圈），
不是抓丢了内容。这类直接丢弃。

### 5.2 入库 + 规则归类

```
原始 HTML → 解析 contentData → 粗筛（是不是面经）→ 入库 posts
                                        ↓
                        逐行判定是否为问题 → 复合题拆分
                                        ↓
                        归类模块/主题 → 模糊聚类 → 落库
                                        ↓
                        重建后清理「一条题都没抽出来」的帖子
```

噪声有四道闸：前两道在抓取侧（便宜，先挡掉大部分），后两道在入库侧（精确，负责收尾）。

| 闸门 | 位置 | 判据 |
|---|---|---|
| ① 空内容 | `LooksLikeInterview` | 标题与正文都为空（打卡动态） |
| ② 题解/广告 | `IsRecruitAd` | 有强广告词（`内推码`/`招聘详情`/`热招岗位`…）**且**面试信号 < 2 处 |
| ③ 非问题行 | `IsQuestion` | 见下，其中一批规则是**用模型标注反推**出来的（见 5.5） |
| ④ 零题目帖子 | `PruneEmptyPosts` | 一条题都抽不出来 → 整帖删除 |
| ⑤ 模型判定 | LLM 归类 | 最终权威：判为「非题目」的默认不展示（见 5.3） |

> ⚠️ **强广告词表里的「内推码」漏掉了不带「码」字的写法。**
> 「华为27届校招内推」「阿里27届校招内推开始啦！」这类标题里只有「内推」两个字，
> 一个强广告词都命中不了，于是**整类内推广告漏过粗筛**，白抓、白解析、再被清理掉。
>
> 补上裸 `内推` 之后实测：新增命中 **67 篇**，其中只有 **5 篇**真有有效题
> （精确率约 92%），而那 5 篇还会被「面试信号 < 2」这道闸再挡一次。
> 复测粗筛通过量 **3,326 → 3,177**（−149 篇广告），零题帖子 **375 → 309**。

**② 为什么用「对比」而不是「命中」**：内推广告的标题常带「秋招/校招」，会命中面经关键词；
内容又常写成「投递方式：1. 2. 3.」加「项目经历」等备赛建议，
所以**单看任何一侧都会误判**。判据因此是「广告信号 vs 面试信号」的数量对比。
真面经偶尔也在结尾挂内推码，但那种帖子面试信号必然远多于 2 处，不会被误杀。

**③ 非问题剔除**（`IsQuestion`）——剔除四类：
- 面试进展/结果描述：`过了已约二面`、`预估一两周才能出结果`
- 面后感/吐槽：`面试官有点装`、`30min搞完，感觉可能会是kpi面`、`双机位面试确实有点难绷`
- 整行括号补充：`（过程中还收到阿里电话，后面也打不回去了）`
- 算法行备注：`手撕：花了挺久`

#### 第三个召回缺口（也是最大的一次）：一行里连排了几十道题

> ⚠️ 不少帖子把题目**连排在一段里、没有任何换行**：
>
> ```
> Java 基础 == 和 equals 的区别？hashCode 为什么要一起重写？String 和 StringBuilder 区别和使用场景？…
> 请做一下自我介绍。你的专业偏开发，为什么选择测试开发岗位？你对测试开发岗位有什么了解？…
> ```
>
> 逐行抽取时整段只算「一行」，于是**几十道题被当成一道**，
> 还会被 1000 字的列宽截断（表现为 canonical 长度正好等于 1000）。
> 实测有 **248 行**是这种形态，其中一份「高频面试题清单」一段就含着 50 多道题。

修法是 `splitInlineQuestions`：**长度 >40 且问号数 ≥2 就在每个问号后切一刀**，
切出的片段各自走后面的判定流程。

| | 修复前 | 修复后 |
|---|---|---|
| 问题簇 | 20,631 | **22,130**（+1,499）|
| canonical 被截断（=1000 字）的题 | 248 | **0** |
| 某篇 B站测试开发一面产出的题数 | 1 | **32** |

两个条件都是必要的：短句不拆（避免把「这样对吗？还是那样？」这种一问两半拆散），
只有一个问号的长句也不拆（那是一整道题）。
测试：`TestSplitInlineQuestions`、`TestExtractSplitsInlineQuestions`。

**残留**：还有 183 条 >120 字，是「把题目写成没有问号的短语罗列」
（`volatile关键字，是不是只用于多线程场景static修饰局部变量…`）——
没有任何分隔符可切，这一类不再强拆。

**④ 为什么还需要第四道闸**：粗筛靠关键词，总会漏掉「恐怖的秋招」「笔试题求经验」这类
看着像、其实没有题目的帖子。而「一个题目都抽不出来」是**数据自己给出的结论**，
不需要再猜规则——它比任何关键词都准。代价是必须先入库再删，所以放在 `ReplaceQuestions`
之后执行（那时 `occurrences` 才是最新的，见 `store.PruneEmptyPosts`）。

> ⚠️ **第 ④ 道闸只能用来杀噪声，杀之前必须先确认召回没问题。**
> 本项目真实发生过一次：`Extract` 早先用 `p.Company == ""` 判断「不是面试帖」，
> 而 `company` 来自「公司 岗位 轮次」这个**严格**格式。
> 于是「上海某量化开发 一面」（只有一个空格）、「遥望科技 hr面」「转转 FDE 线下面试」
> 这批真面经被整篇跳过——库里表现为它们 0 个出现记录，
> 和「打卡动态」这种真噪声长得一模一样。
> 若当时直接跑 `PruneEmptyPosts`，删掉的就是真数据。
>
> 修复方式是把判据从「company 是否解析出来」换成「标题里有没有面试信号」
> （`isInterviewPost`），并加了回归测试 `TestExtractDoesNotDropTitledInterviews`
> （已验证：改回旧逻辑测试就红）。
> 效果：问题 1478 → **1576** 组，出现记录 1520 → **1611** 条，
> 真正空的帖子从 13 篇降到 **4 篇**。
>
> 教训：**「数据为空」有两个来源——帖子是噪声，或者抽取漏了。**
> 用一个宽松的代理指标（company）去区分它们，会把后者误判成前者。

**复合题拆分**（`SplitCompound`）——只对算法行生效：

```
手撕：大数相加 & 接雨水  →  手撕：大数相加 / 手撕：接雨水
```

其他题型里的 `&`、`、` 往往是同一道题的并列成分（「上下文管理、Skill 和 MCP 的理解」
是一道题），拆分反而错。

**聚类**：归一化保留英文数字（`DNS`/`gRPC`/`Go` 才是技术题的主体）+ Levenshtein 阈值 0.82。

**归一化要先剥掉行首编号/标签。** 面经里普遍把题目写成「7.xxx」「4、xxx」
「(3) xxx」「第3题 xxx」「Q：xxx」「面试问题：xxx」，不剥的话同一道题会因为编号不同
聚成两簇，频次统计被拆散（实测 4296 组有效题里有 7 对这样的重复，剥掉后合并了 45 簇）。

> ⚠️ 这里有个反例要防：「**3.2 版本**的 Go 有什么变化」里的「3.」是**版本号**不是题号。
> 规则是「分隔符后面紧跟数字就放弃剥离」，因为 Go 的 RE2 不支持 lookahead，
> 这一步只能用代码判断而不是纯正则（`stripLeadLabel`）。
> 测试：`TestStripLeadLabelKeepsVersion`。

展示用的 `canonical` 也会剥掉这层前缀（「7.算法：最大子数组和」→「算法：最大子数组和」），
但原文措辞完整保留在 `occurrences.raw_text` 里，不丢信息。

#### 合并判据必须用「稳定锚点」，不能用会变的键

> ⚠️ **这是全项目最严重的一次数据质量事故。**
>
> 现象：一个簇吃掉了 **2063 个变体、360 次出现**，成员从「智能指针」到
> 「agent runtime」到「YUV 格式」毫无关系。其余簇最大只有 60——
> **这种量级断层就是聚类出错的信号**（真实面经里同一道题被问到几十次就到顶了）。
>
> 成因是两个问题叠加：
> 1. 合并判据用的是 `g.norm`，而 `norm` 取「簇内最长/官方那条的归一化文本」，
>    会随着新成员加入**变长**——簇的身份在漂移；
> 2. 判据里有 `strings.Contains(锚点, n)`，长锚点会把任何碰巧作为子串出现的
>    短问题吸进来。
>
> 再加上「并入第一个匹配簇」的单链接策略，就成了链式吞噬：
> A~B、B~C、C~D……即使 A 与 D 毫无关系。
>
> 修法两步：
> - **合并只用进簇第一行的 `key`（永不改变）**，每一步都只与起点比较，链自然断掉；
> - 包含关系加**长度比上限 2 倍**：真人问同一道题的两种写法长度不会差太多，
>   而长句子当锚点时会吞掉所有短子串。
>
> 效果（同一批原始数据重新聚类）：

| | 修复前 | 修复后 |
|---|---|---|
| 问题簇 | 8072 | **11925**（+3853）|
| 最大簇频次 | 360 | **60** |
| 有效题 | 4957 | **7111**（+43%）|
| 带答案的有效题 | 1529 | **2429** |

> 回归测试三条：`TestClusterAnchorDoesNotSwallowShortQuestions`（已验证：去掉长度比
> 限制它就红）、`TestClusterAnchorIsStable`、`TestClusterNormalRealisticDistribution`。
>
> 教训：**聚类的合并判据必须是单调稳定的**。任何「用簇内内容重新计算出的键」
> 去参与合并判断，都会让簇的身份随内容漂移，在单链接策略下必然失控。

#### 聚类质量怎么验

「锚点稳定 + 只与锚点比较」会不会反过来导致**该合的没合**？用全量数据量过：

| 指标 | 结果 |
|---|---|
| 归一化后完全相同的重复组 | **0**（有的话说明确定该合而没合）|
| 相似度 ≥0.82 却仍分开的重复对 | **8 对 / 7029 条 = 0.11%** |
| 最大簇频次 | 60（修复前 360）|

那 8 对是「代表措辞相近但锚点不相近」造成的——这是锚点稳定策略的固有代价，
量级 0.11%，且全是 n=1 的长尾，对频次统计没有实际影响，
所以没有再叠加一轮「按代表措辞再合并」的后处理（那会重新引入漂移风险）。

**排查手法值得记下来**：把全部题目的归一化文本两两比相似度。
按首字分桶可以把 2400 万对降到 12 万对，几秒就算完。

### 5.3 LLM 归类（三步解耦）

| 步骤 | 命令 / 产物 | 做法 |
|---|---|---|
| ① 探索 | `make llm-sample` → `data/llm/sample.json` | 按规则模块**分层抽样**（不分层会被大模块淹没，尾部模块全落「其他」），让模型据此产出 `taxonomy.json` |
| ② 归类 | `make llm-batches` → `batches/batch-NN.json` | 每批 150 条；子代理读批次、写 `out/batch-NN.json`（**每条必带 text**） |
| ③ 合并 | `data/llm/merge.json` | 人工决定「细分类 → 可用类」的映射 |
| ④ 应用 | `make llm-apply` | 写 `llm_labels` + 物化到 `questions.llm_*`，并写入 `taxonomy` 表 |

**为什么分开**：合并规则变了只需重跑第 ③ 步（`make llm-apply`），**不必再调模型**。
三层都留在库里（`llm_merged` / `llm_domain` / `llm_cat`），随时可换合并方式。

#### 标注的存储：按题目文本，不按行 id

**标注存在 `llm_labels(norm PRIMARY KEY, cat)`，`questions.llm_*` 只是它的物化视图。**
每次 `ReplaceQuestions` 结束都会按 norm 把它回填到新行。

这不是设计洁癖，是两次真实事故换来的：

> **事故一：标注随失败的重建一起消失。**
> 原来 `llm_cat/llm_domain/llm_merged` 只存在 `questions` 里，而 `questions`
> 每次 rebuild 都被 TRUNCATE。保护措施是「重建前读进内存、建完按 norm 写回」——
> 但它只覆盖**成功路径**。一次重建在插入循环里因为
> `Error 1406 Data too long for column 'norm'` 中途失败，TRUNCATE 已经执行、
> 写回永远不会执行，**1477 条模型标注全部丢失**。
>
> **事故二：按 id 落地会静默贴错标签。**
> 恢复时把 `data/llm/out/*.json` 重新 apply 了一遍，但那些文件只存 `{id, cat}`，
> 而 id 是重建后重排过的自增主键。于是 1478 条标注被贴到了**完全无关**的题目上，
> 实测旧 id 与当前题目的匹配率是 **0/212**。
> 最糟的是它不报错：`UPDATE ... WHERE id = ?` 对每个 id 都「成功」。

修法：
- 标注单独存 `llm_labels`，主键是题目归一化文本——**题目文本是稳定的业务键，id 不是**。
- 批次文件（`out/batch-*.json`）**必须带 `text` 字段**；缺 text 的结果会被
  拒绝导入并计数（`NoText`），而不是猜一个 id 贴上去。
- 导入走 `ApplyClassificationsByNorm`，写完按 norm JOIN 回填。
- 回归测试：`TestLabelsRecoverAfterQuestionTableReset`（模拟「重建中途失败」后
  只剩标注表的状态，验证能恢复；已验证：去掉修复它就红）、
  `TestLabelsSurviveRebuild`、`TestApplyLabelsIgnoresUnknownNorm`。

**合并规则可反复重跑**：`merge.json` 变了只需 `make llm-apply`，不必再调模型。

## 七、API

### 列表接口只返回预览，详情接口返回全文

数据量上去之后，列表响应会迅速变大。实测一页 50 条：

| | 优化前 | 优化后 |
|---|---|---|
| `GET /api/questions?size=50` | 447 KB | **290 KB**（−35%）|
| `...&size=200` | 907 KB | **648 KB**（−29%）|
| `...&size=50&hasAnswer=1` | 315 KB | **151 KB**（−52%）|

做法是把两个「长字段」在列表里截断：

| 字段 | 列表里 | 详情里 | 前端的兜底 |
|---|---|---|---|
| `answer` | 前 400 字 | 完整 | `answerLen` 是原始长度，>`answer` 长度就显示「完整答案 N 字 · 点击加载」，点开按 id 取全文 |
| `occurrences` | 最多 20 条 | 完整 | `n` 是真实频次，`n > 已显示条数` 就显示「另有 N 条出现记录」 |

**为什么不干脆都放详情里**：列表要显示「答案」标记和「被问到的场合」，
一条都不给就得每张卡片各发一次请求。截断预览让首屏自足，同时把响应压到三分之一。

> ⚠️ 契约要点：**`answer` 在列表里不是全文**。任何消费方要完整答案都得调
> `GET /api/questions/{id}`。这一条容易踩，因为列表里的字段名和详情里一样。



| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查 |
| GET | `/api/meta` | 概览统计 |
| GET | `/api/facets` | 全部筛选维度及计数 |
| GET | `/api/taxonomy` | LLM 分类体系（三层） |
| GET | `/api/topics?category=` | 模块下的主题 |
| GET | `/api/questions` | **问题列表**（多维筛选 + 分页） |
| GET | `/api/questions/{id}` | 单问题 + 全部出现记录 |
| GET | `/api/posts` | 帖子列表 |
| GET | `/api/posts/{id}` | 帖子详情（含正文） |
| POST | `/api/reimport` | 用库内帖子重建聚类 |

`/api/questions` 参数：

| 参数 | 取值 |
|---|---|
| `round` | 一面 / 二面 / 三面及以上 / HR 面 / 复活赛 |
| `job` | Agent 开发 / 全栈开发 / 平台·Infra / … |
| `company` | 任意公司名 |
| `category` `topic` | 规则分类 |
| `llmMerged` `llmDomain` `llmCat` | 模型分类三级 |
| `q` | 关键词（匹配代表措辞与全部变体） |
| `sort` | 空＝按频次；`co`＝按公司覆盖面；`priority`＝复习优先级 |
| `from` `to` | 发布时间闭区间（`YYYY-MM-DD`）。**全局**：统计卡、维度计数、矩阵、原文列表都受它约束 |
| `page` `size` | 默认 1 / 50（上限 500） |

`sort=priority` 的权重是刻意写成**可解释**的，而不是调出来的黑箱：

```
co_n * 3 + LEAST(n, 20) + (有参考答案 ? 4 : 0)
```

公司覆盖面权重最高——被 20 家公司各问一次，比被同一家公司问 30 次更能说明
「普遍要会」。`n` 取 20 封顶是为了防止「一家公司刷很多帖」把分值顶穿。
`co_n` 在 `RecomputeCounts` 里与 `n` 一起重算，保证重建/去重/合并之后两者自洽
（回归测试 `TestRecomputeCountsSetsCompanyCoverage`、`TestQueryQuestionsSortByCoverage`）。

另有 `GET /api/matrix?companies=14&cats=12`：返回「公司 × 知识点」交叉计数，
单元格是**去重后的题目组数**（同一道题被同一家公司问多次只算 1），
供前端的「公司×知识点」矩阵页使用。

### 列表接口的响应体积

出现记录（`occurrences`）曾占列表单条响应的近九成（实测 5.6KB/6.3KB），
而它们只在展开时才需要看。现在列表只带前 **6** 条，展开时前端按 id 取完整列表
（详情接口本来就返回全部）。

同义合并之后又冒出第二个大头：**「其他措辞」**。榜首那几条题动辄有几十种写法
（实测合并后的「自我介绍」有 **72** 种），全带上单条多出近 1KB。
所以列表的 `variants` 也封顶到 **12** 条，并新增 `variantN` 字段告诉前端总数。

两处封顶合计：`/api/questions?size=20` 从 **约 160KB 降到 70KB**。

前端筛选状态同步到 URL hash，可直接分享：

```
http://127.0.0.1:8787/#llm?llmMerged=MCP%20%E4%B8%8E%20Skill
```

## 八、面经原文页：为什么用「有没有有效题」而不是广告关键词

「面经原文」页签直接翻帖子全文（题目列表切掉了作者的完整叙述：
面试流程、节奏、问到什么深度、怎么被追问）。但原始语料里混着大量内推广告。

原本想加强广告关键词规则，**拿库内数据量过之后否掉了**：
标题含「内推」的帖子有 432 篇，其中 276 篇是纯广告。按「面试/面经出现次数」
当阈值来拦：

| 阈值 | 拦下纯广告 | 误伤真面经 | 精确率 |
|---|---|---|---|
| <2 | 32/276 | **47/156** | 40.5% |
| <3 | 192/276 | **114/156** | 62.7% |
| <4 | 255/276 | **127/156** | 66.8% |
| <5 | 268/276 | **132/156** | 67.0% |

**最高只有 67%**——想拦 255 篇广告就得误杀 127 篇真面经（它们只是结尾挂了内推码）。
关键词阈值这条路在这个问题上不成立。

改用「**这条帖子有没有一道没被判为非题目的题**」：
它是模型逐条判定后的结论，而不是字面猜测。

```
默认（只列有有效题的）  886 篇
all=1（全部）          1548 篇
```

判据用的是「未被判为 非题目」而不是「已归类」——未归类 ≠ 噪声，
不能因为归类还没跑就把帖子藏起来；这样也天然覆盖全新部署（没有标注时全部通过）。

> 这是**展示侧过滤，不删数据**。帖子仍在库里，`?all=1` 可以看到全部。
> 测试：`TestPostsHidesAdOnly`。

## 九、从零部署的验证结果

部署步骤不是照抄配置写出来的，而是在**空库**上真跑过一遍（2026-09-13）：

```
① 空库启动服务          → 6 个 migration 全部按序应用成功
② make parse            → 691 篇入库，0 条解析失败，含 117 篇带结构化真题
③ make rebuild          → 5183 组问题 / 6699 条出现记录
④ make llm-apply        → 4787 组归位（91.5%），判出「非题目」2727 组
```

**migration 全部按序应用**：`001_init` → `002_llm_taxonomy` → `003_sources`
→ `004_official` → `005_widen_norm` → `006_llm_labels`，无报错。

> ② 的 691 篇比生产库的 523 篇多，是因为这一步没跑 `-prune`
>（它删掉一条题都抽不出来的帖子）。文档里推荐的 `make parse` 会带上 `-prune`。
>
> ④ 的 91.5% 而不是 100%，是因为**标注按题目文本匹配**：
> 空库重建时聚类顺序不同，代表措辞可能选到另一条，于是少量 norm 对不上。
> 这是「按文本而不是按 id」的必然代价，但换来的是**重建不会丢标注**
>（见 5.3 的两起事故）。未命中的题可用 `make llm-batches` 增量补归类。

## 十、故障排查

| 现象 | 原因 / 处理 |
|---|---|
| `Error 1045 Access denied` | `.env` 里 `NC_DB_PASS` 不对，或用户未建 |
| `Error 1819` 建用户失败 | 密码不满足 `validate_password`（见步骤 1） |
| 服务启动 `duplicate column` | migration 追踪失效；检查 `schema_migrations` 表 |
| 前端「原文 ↗」链接消失 | **JSON 字段名被改**。前端读 `occurrences`，见 `internal/model/model_test.go` |
| 界面能开但列表空 | 后端未启动或 CORS/端口不符；看浏览器控制台 |
| `reimport` 后数据变少 | 历史 bug（已修）：`Posts()` 的 size 钳制把「取全部」压成 50，改用 `AllPosts()` |
| 抓取返回 HTML 而非 JSON | 主机/参数写错：`gw-c.nowcoder.com` + `pageNo` |
| 抓到很多 6KB 的页面 | 站点软限流返回空壳页。`make fetch-check` 清理后重抓；算法侧已自动识别并重试 |
| 帖子日期是 1970 | `createdAt` 为 null 的老帖。已用 `editTime` 兜底；历史数据重跑 `make parse` 即可修正 |
| 库里全是内推广告 | 粗筛的广告判据过期。更新 `reKwAdStrong` 后 `make parse` 重跑（原始 HTML 还在） |
| 抓一半断了 | 正常。原始响应已落盘，重跑 `make fetch` 自动续抓 |
| 抓取很慢（单请求 >2s） | 空壳页被当成限流做了退避。看进度行的「单请求」指标；正常应 ≈0.5s |
| parse 报少量「解析失败」 | 与抓取并行时读到写了一半的文件。`Save` 已改为原子 rename；重启抓取进程生效 |
| `Error 1052 ... ambiguous` | `ON DUPLICATE KEY UPDATE` 里用了裸列名。必须写成 `posts.x` |
| `converting NULL to string` | 新加的列是 NULL。查询里要 `COALESCE(col,'')` |
| `Error 1406 Data too long` | 题目是完整句子，超了 `norm` 列宽。写入前用 `model.ClipRunes` 截断 |
| 插入“失败”但日志只有一行 | 检查是不是 `Error 1052` —— 它会让**所有**插入失败，但只打印一次 |
| LLM 标注全没了 | 重建中途失败导致。现在标注存在 `llm_labels` 表，重建后自动按 norm 回填；用 `make llm-report` 确认覆盖 |
| `llm-apply` 报「缺少 text 字段」 | 旧格式的 `out/*.json` 只有 id。id 会随重建重排，按 id 落地会静默贴错标签，必须重新生成带 text 的批次 |

## 十一、已知边界

1. **`company`/`job`/`round` 依赖标题格式**——只有「公司 岗位 轮次」这种标题能解析。
   通用面经的标题千奇百怪，这三个字段会为空。
2. **规则分类的模块边界是启发式的**——「Go 的协程调度」归后端工程而非计算机基础，
   是刻意选择但并非唯一正确答案。
3. **LLM 归类无完全一致标准**——10 个批次各自判断，边界题会有差异。细分类保留就是为了便于重合并。
4. **非题目 40 条仍会出现在「不选任何知识点」的默认列表**（选中任一知识点即自动排除）。
5. **搜索是 `LIKE` 而非全文索引**——1576 条下够用，量级上去需要 `FULLTEXT ... WITH PARSER ngram`。
6. **无鉴权**——服务默认只绑 `127.0.0.1`；对外暴露前必须加认证与 `--trusted-host`。

## 十二、安全与合规

- **只抓公开内容**，严格遵守 robots.txt（仅 `/search`、`/nccommon`、`/ab/` 被禁）。
- **凭据只从环境变量/`.env` 注入**，`.env` 与 `scripts/*.local.sql` 均已 gitignore，权限 600。
- **限速**：全站抓取为 **4 个分片并行**，每片内随机 2~5s/请求 + 每 25 条长休息 10~30s，
  并有跨进程断路器：任一 worker 发现空壳率超过阈值就让**所有分片一起停**（冷却逐次翻倍，10 分钟封顶）。
  实测聚合约 0.65 条/秒。
- **站点软限流是设计内行为**：返回空壳页时会自动降速并重试，不是故障（见第十三节）。
- **内容为 UGC**，版权属发帖人；仅供个人学习，请勿再分发或商用。

### 5.4 标题字段的宽松解析（公司 / 轮次 / 岗位）

`ParseTitle` 只认「公司 岗位 轮次」这种严格格式，那是**一个用户**的写作习惯。
抓全站后发现绝大多数标题是自由写法：

```
美团9.12笔试大家aicoding和编程通过多少？
Minimax 秋招后端三面
momenta后端一面
11.9金山WPS-服务端笔试
```

结果是 `company` 大面积为空，**「按公司筛选」这一整个维度在全站数据上近乎失效**
（实测 sitemap 帖 198 篇里只有 11 篇解析出公司）。而「我想看某家公司的面经」
恰恰是这个站点最核心的用法之一。

于是补了一条宽松路径（`internal/scraper/title.go`）：

| 字段 | 来源 | 覆盖（全站样本） |
|---|---|---|
| 公司 | 严格格式 → 词典最长匹配 → 「轮次词之前那段」启发式 | **77%**（原 3.6%） |
| 轮次 | 在标题里**任意位置**找 一面/二面/三面/HR面/笔试/测评/群面… | 26% |
| 岗位 | 在标题里任意位置找 后端/前端/算法/Agent/嵌入式/游戏/数据… | 31% |

公司数从 **73 → 167**。

#### 三个关键设计

**① 词典会自己长大。** 种子表只有几百个常见公司名，但 `cmd/parse` 每次运行
都会把库里已有的 `company` 值一起喂进来。一家公司在任何一篇**标准格式**标题里
出现过，之后它出现在自由标题里也能被认出来——词典随抓取自动扩充。

**② 精度比召回重要。** 这个维度填错了会让人按公司筛出**完全无关**的题；
漏掉只是少一个筛选入口。所以：
- 单字一律不算公司名
- 「猜」只在标题里**确实有轮次词**时才做（没有轮次词就没有切分依据）
- 候选片段含句号、逗号、问号，或以「了/吗/吧/呢」结尾 → 不是公司名
- 剥掉岗位/批次词后只剩「智能」「技术」这类通用词 → 放弃

**③ 回填必须自愈。** `backfillMeta` 对**全部**帖子重算标题字段，
而不是只处理字段为空的。理由是解析规则会改，而按旧规则填错的值得被纠正——
只挑空字段的写法永远碰不到它们。

> ⚠️ **踩过的两个坑**（都补了回归测试）：
>
> 1. **`TA\b` 把 `momenTA` 认成「技术美术」。** Go 的 `\b` 是 ASCII 语义，
>    「后」不算 ASCII 词字符，所以 `ta` 后面算边界。位置词表里不能用 ASCII 边界锚。
> 2. **词典污染放大成 79 篇错帖。** 一个单字「招」混进词典后，
>    `strings.Contains` 让**所有含「招」的标题**（秋招/校招/招聘/招银…）
>    全被认成同一家公司。两道防线：单字不算公司名；**词典命中的结果也要过校验**。
>    测试：`TestLexiconPoisoningResistance`。

#### 轮次兜底：只认正文里的「标题式行」

标题能给轮次的只有约一半。为补上剩下的，加了一条从正文兜底的规则，
但**第一版写错了，而且错得很隐蔽**——详见 `docs/RETROSPECTIVE.md` 问题 11。

规则最终定为：

- 逐行扫描正文，先剥掉行首的列表符 / 编号 / 括号 / 空白；
- 只认**整行 ≤24 字、且以轮次词开头**的行（即「标题式行」）；
- 把轮次归一成「键」：`一面`/`第一轮`=1、`二面`/`第二轮`=2、`三面`/`第三轮`=3、
  `四面`=4、`终面`=5、`HR面`=hr（HR 不要求出现在行首，`第三轮HR面`也算 HR）；
- **恰好一种键**才采用；出现两种以上（帖子横跨多轮）或一种都没有，都留空。

**为什么必须这么严**：在正文里任意位置搜轮次词，会把一批「八股合辑」整篇标错。
《嵌入式CAN总线必备八股文总结》正文只有一句叙述「一面却卡在第一层」，
整篇 40 道通用八股就被算进了「一面」这个筛选项。同一批数据实测：
宽松版 129 篇 / 1,544 题 → 收紧版 **20 篇 / 279 题**，剔掉的 122 篇正是这类叙述性提及。

**为什么用「键」比较**：正文同时有 `第一轮技术面` 与 `第三轮HR面` 的帖子，
键是 {1,hr}，单看正文判断不了某道题属于哪一轮——**留空比标错好**。

回归测试：`TestRoundFromContent`、`TestRoundFromContentNeverReturnsAmbiguous`。

### 5.5 用模型标注反推规则（数据驱动的噪声闸门）

第 ④ 道闸（`PruneEmptyPosts`）之后还有一层：**把模型判出来的 2466 条「非题目」
当成标注集，反推高精确率的关键词规则**，再加到 `IsQuestion` 里。

这样定规则的好处是不会凭直觉误杀——每条规则都要先证明「命中的绝大多数确实是噪声」。

做法：拿 2466 条「模型判定为非题目」+ 3863 条「模型判定为有效题」，
对每个候选规则算**精确率**（命中里真的是噪声的比例）与**覆盖**（能拦下多少噪声），
只把精确率 ≥94% 的加进去：

| 规则 | 命中噪声 | 误伤有效 | 覆盖噪声 | 精确率 |
|---|---|---|---|---|
| 面试指导语（`面试官想听/面试时/回答这类`…） | 35 | 0 | 1.4% | **100%** |
| 内推/招聘信息（`内推码/招聘/投递链接`…） | 226 | 3 | 9.2% | **98.7%** |
| 话题标签行（`#秋招# #面经#`） | 92 | 5 | 3.7% | **94.8%** |
| 第一人称回忆（`我已经/我当时/鼠鼠`…）+ 长 + 无问号 | 12 | 1 | 0.5% | 92.3% |
| 攻略结构词（`第 N 步/第 N 遍/划重点`）+ 长 + 无问号 | 12 | 1 | 0.5% | 92.3% |
| Markdown 痕迹（`- xxx` / `**加粗**`） | 230 | 12 | 7.3% | 95.0% |
| 长 + 无问号 + 代码片段（`->` / `.method(`） | 171 | 2 | 3.0% | 98.8% |
| 含 URL（`https://` / `.com/`） | 178 | 7 | 1.9% | 96.2% |
| 无问号 + 编程语言关键字（`return`/`class`/`static`…） | 288 | 22 | 3.1% | 92.9% |
| 注释前缀（`备注：`/`注：`/`说明：`） | 18 | 0 | 0.2% | 100% |
| 极短编号残片（`1.abc`，**仅 ASCII**） | 18 | 1 | 0.2% | 94.7% |
| 长 + 无问号 + 求职过程词（`秋招/投递/简历/offer`…） | 127 | 10 | 4.0% | 92.7% |
| 长 >40 且无问号（**未采用**） | 436 | 118 | 17.7% | 78.7% |
| 含建议词（**未采用**） | 85 | 85 | 3.4% | 50.0% |
| 语气结尾（**未采用**） | 30 | 25 | 1.2% | 54.5% |

（这几行是标注集逐轮变大后**重新统计**出来的：2466 → 3152 → 5695 条。
样本变大后不断有新规则过线，实测上线效果：噪声簇 **−318**，有效题只 **−2**。）

> ⚠️ **一个隐蔽的失效：URL 的查询串会让所有噪声规则失灵。**
>
> 「没有提问意图才生效」的那批规则都依赖 `asking` 判定，而 `asking` 看的是
> 「这行有没有 `?` 或 `？`」。可 URL 的查询串自带 `?`：
>
> ```
> 投递入口：https://jobs.mihoyo.com/m/?sharePageId=142899
> ```
>
> 这行因此被当成**问句**，于是所有噪声规则全部跳过——URL 规则自己也拦不住它。
> 修法是判定 `asking` 前先用 `reStripURL` 把 URL 抠掉。
> 实测修完这一处，同一批数据上噪声簇再降 115 条，而**有效题一条没少**。
>
> 教训：**启发式判据会被「不该算进来」的字符污染**，而污染是静默的。
> 同一类问题还有：URL 里的 `/` 会被当路径分隔符、代码里的 `()` 会被当括号补充。

#### 一个更该记的教训：统计口径错了，数字再漂亮也没用

> ⚠️ 上面那条「极短编号残片」规则的第一版写的是 `^\d{1,2}[、.．]\S{1,8}$`，
> 把**中文**也算进了「残片」。后果是把「1. 自我介绍」「7. 什么时候要用锁」
> 「8. 面向对象的特性？」——**最常见、最规范的编号真题**——整类丢掉。
>
> 拿帖子正文逐行量过：**996 行命中，其中 988 行含中文，全是真问题。**
>
> 为什么统计时没发现？因为那条规则的精确率是在 `questions.canonical` 上算的
> （94.7%，18 条噪声 / 1 条有效），而 **canonical 的编号早被 `stripLeadLabel` 剥掉了**，
> 命中的那 18 条根本不是「编号开头的题」。**统计口径和被保护的对象对不上，
> 得到的是一个漂亮但无关的数字。**
>
> 改成只匹配「编号后面只剩 ASCII」（`1.abc`）之后，同一批数据上恢复
> **+176 簇 / +68 有效题**。
>
> 这条与第 5.5 节的方法论不矛盾，而是它的补充：
> **反推规则时必须确认「统计用的样本」和「规则实际作用的对象」是同一个群体。**
> 这里的统计对象是聚类后的代表措辞，规则作用的却是聚类前的原始行——
> 两者在「编号」这个维度上恰好相反。

**规则提炼已经进入平台期。** 标注集涨到 5695 条非题目 / 8337 条有效题之后，
重新统计了 10 条候选规则，只有「代码片段」一条过 92% 的线，
其余都在 60%~85% 之间（「含『：』」80.4%、「含『考察/考点』」75.2%、
「含『我』」72.1%）。原因是**剩下的噪声在表面形态上已经和真题无法区分**——
比如「讲一下你对虚拟资产交易的理解」和「讲一下你对Agent评测体系的理解」
是同一句式，一条是真题、一条也是真题；而「回答这类问题时…」开头的攻略
与真题的差别只在语义，不在字面。

也就是说：**规则层能拦下的噪声已经基本拦完了**，剩下的必须靠模型逐条判断。
这也解释了为什么噪声占比稳定在 40% 左右不再下降——
它是这份语料的固有成分，不是过滤没做好。

**只有 92% 以上的被采用。** 「长 + 无问号」看着能拦下 436 条，但精确率只有 78.7%
（会误杀 118 条真问题）；「含建议词」更是只有 50%，等于乱杀。这类"看起来有效"的规则
正是凭直觉写规则时最容易犯的错。

**所有新规则都要求「没有提问意图」**：真问题里出现「招聘」「面试时」非常正常
（「你们的招聘流程是怎样的？」），带问号就必须放行。

> 这套做法可以复用：只要有一批**模型标注**，就能把「模型知道但规则不知道」的模式
> 提炼成便宜、可解释、可测的规则。代价是模型标注本身要先跑一次。

#### 规则层与模型层的分工

| | 规则层（`IsQuestion`） | 模型层（LLM 归类） |
|---|---|---|
| 位置 | 入库前 | 入库后 |
| 倾向 | **召回优先**（默认是题目，只剔除明确不是的） | **精确优先**（逐条判断） |
| 成本 | 免费 | 约 150 条/子代理 |
| 作用 | 挡住大头噪声，减少模型工作量 | 最终判定，也是「非题目」的唯一权威来源 |

**默认列表隐藏的是模型判定的「非题目」，不是规则判定的。** 因为规则刻意宁松勿严，
留下的漏网噪声只能靠模型收尾。

### 5.6 官方结构化真题（质量最高的题源）

牛客的内容页里，`ssrCommonData` 下与 `contentData` **平级**的地方有一个
`experienceQuestionList`——发帖人/官方把这场的题目整理成了结构化列表：

```json
[{"id": 2654827, "entityType": 3013,
  "title": "项目当中强化学习框架怎么搭建的",
  "answer": "- 正确答案：在项目中搭建强化学习框架通常遵循…"}]
```

实测（531 条样本）：

| 指标 | 数值 |
|---|---|
| 带该列表的帖子 | 4.3% |
| 平均每帖题量 | **11.1 条** |
| 带参考答案的比例 | **100%** |
| 按全站推算 | 约 1,100 篇帖子 → **约 1.2 万条带答案的题** |

**这是什么量级**：正文正则抽取的产出率是「26.7% 的帖子像面经 × 每篇几道题」，
换算下来每 100 条 URL 大约出 100 道题（还有噪声、没答案）；
而结构化真题每 100 条 URL 出 **48 道**干净且带答案的题。
**后者的单位抓取成本更低、质量高一个量级**，是目前最有价值的数据源。

#### 管线

```
抓取 → ExtractContent 解析 experienceQuestionList
     → cmd/parse 序列化存进 posts.official_q（JSON）
     → importer.officialRows 展开成题目行
     → 与正文抽取的题一起聚类（同义题会合并，频次叠加）
     → questions.answer 保存参考答案
     → occurrences.official 标记来源
```

#### 三个刻意的设计选择

**① 存 JSON 列而不是建表。** `posts.official_q` 只被 importer 读一次用来生成题目，
不需要单独查询。建一张表就多一份要维护的同步关系，收益为零。

**② 官方真题不经过 `IsQuestion` 启发式过滤。** 那些判据（「面试官有点装」
这类是面后感不是题）是给**正则从正文里抠出来的行**用的。官方列表本身就是
题目的权威定义，再拿启发式规则去筛只会误杀——「自我介绍」在正文里常被当套话，
但它确实是真题目。

**③ 有官方真题的帖子一定算面经帖。** 即使标题不符合「公司 岗位 轮次」格式、
也不含任何面试关键词，只要有结构化真题就必须参与抽题。

#### 展示与筛选

- `questions.answer` 存参考答案；`COALESCE(answer,'')` 读出（NULL 与空串语义不同）
- 前端在卡片展开区渲染答案，并在折叠行上给「真题 / 答案」两个标记
- 提供两条质量筛选：`?hasAnswer=1`（只看有答案）、`?officialOnly=1`（只看官方真题）
  ——「有答案 ≈ 官方整理过 ≈ 质量更高」，这是「我想系统刷题」和
  「我只想看看都问什么」之间的分界线

#### 已知的数据质量问题：答非所问的答案

官方真题的答案由模型生成。**题目过于简短或指代不明**时（「我的输出是什么」
「讲解以下主要区别」「用什么方法解决」），生成答案的模型会反过来**请求澄清**
而不是作答：

```
题目：HTTPS如何保证通信安全？TLS密钥是怎么协商的？
答案：看起来您的输入可能不完整，只发送了一个"https"。请问您是想了解…
```

还有一类是**以 AI 自居**回答（题目在问「你做过什么项目」，答案在说
「作为AI助手，我本身不是 Agent 项目的开发者…」）。

这类内容留在题库里比没有答案更糟——用户点开「参考答案」看到的是模型在问他要题。
所以 `isMetaAnswer` 会在入库时把这类答案清空（**题目保留，只丢答案**）。

> ⚠️ **判定顺序踩过一个坑**：官方答案的原文形态是「`- 正确答案：<正文>`」。
> 早先的实现**先判定、后剥前缀**，于是开头被前缀挡住，
> 6 条「作为AI助手，我本身不是…」一直没被过滤掉——而且不报错，
> 只有去 DB 里数才看得出来。现在先 `TrimAnswer` 再判定。
> 回归测试：`TestPrefixedMetaAnswerIsFiltered`。
>
> 判据只在**答案开头**（前 60 字）匹配，不放宽到全文：
> 实测有条约 2000 字的正常答案中间就出现了「请补充」，全文匹配会误伤。

> ⚠️ **接入新列时踩到的三个 bug**，都是「编译通过、单元测试通过、只有真库才报」：
>
> 1. `ON DUPLICATE KEY UPDATE ... IF(new.x='', x, new.x)` 里的裸列名被 MySQL 判为
>    ambiguous（Error 1052），**所有新帖插入静默失败**（日志只有一行写入失败）。
>    必须写成 `posts.x`。
> 2. `official_q` / `answer` 是 NULL，`Scan` 进 `string` 报
>    "converting NULL to string is unsupported"，让整个聚类重建或问题列表挂掉。
>    读的时候要 `COALESCE`。
> 3. 官方真题是**完整句子**，比正文抠出来的短行长得多，撑爆 `norm` 的列宽
>    （Error 1406 Data too long）。
>
> 这三个都在 `internal/store/store_test.go` 的集成测试里钉住了（需要真 MySQL）。
> **纯函数测不出 SQL 层的错误**——这组测试是为此专门加的。

### 5.6.1 原文链接：`/discuss/<id>` 不能拼成 `/feed/main/detail/<uuid>`

牛客有两种内容页形态，**两者都带 `contentData.uuid`**：

| sitemap 里的形态 | 正确的详情链接 |
|---|---|
| `/feed/main/detail/<uuid>` | 原样即规范链接 |
| `/discuss/<id>?urlSource=sitemap` | `https://www.nowcoder.com/discuss/<id>` |

⚠️ 把 `/discuss/<id>` 的帖子按 uuid 拼成 `/feed/main/detail/<uuid>` 会落到**空壳页**：
HTTP 200、有 `contentData`、**但没有正文**。所以靠状态码或 `contentData` 判断「链接是否有效」
一律会判它正常。实测 1,270 篇（36%）帖子、44,817 条出现记录（64.4%）因此是坏链。

规则：**规范链接优先用抓取时用的 URL**，只在它不是内容页形态时才退回按 uuid 拼。
实现在 `cmd/parse/main.go`，配合 `scraper.IsContentURL`，回归测试 `TestIsContentURL`。

### 5.6.2 全局时间范围（按发布时间筛选）

前端页签下方有一条全局时间栏（预设 + 起止日期），**作用于下面展示的全部内容**：
顶部统计卡、各维度计数、公司×知识点矩阵、题目列表、面经原文列表。

实现上有一条原则：**时间范围必须贯穿每一个数字**。
「筛了 9 月，但公司榜还是全量」这种自相矛盾比不提供筛选更误导，所以：

- `model.Filter.From/To`（`YYYY-MM-DD` 闭区间）→ `store.dateCond()` 生成条件片段；
- 问题列表、`facet` / `facetQ` / `facetLLM` / `TopicFacets` / `LLMCatFacets`、
  `Matrix`、`Posts`、`Meta` 全部接上；
- 前端 `rangeParams()` 统一注入所有接口调用，并写进 URL hash（可分享）。

两个容易漏的点，都已钉在 `TestDateRangeFiltersEverything` 里：

1. **计数口径要换成 occurrences**。原来 facet 直接读 `questions.n`（全量总数），
   带时间筛选时那个数用不了，必须回到 `occurrences × posts` 上按日期重算。
   两种写法在无筛选时结果完全一致，所以统一走后者。
2. **`/api/posts` 是独立查询**，主表没有别名，不能复用 `dateCond` 的片段
   （它写死了别名 `p`）。这一处真的漏过一次——参数加了但没拼进 SQL，
   表现是「原文列表完全不受时间影响」。

> ⚠️ **全局范围与被筛范围是两个字段**。`Meta.DateFrom/DateTo` 跟着筛选变，
> 但时间栏的 `min`/`max` 与「可选范围」提示必须用**不受筛选影响**的
> `Meta.GlobalFrom/GlobalTo`——否则筛过一次之后，输入框的可选范围被收窄到
> 刚筛的那一段，用户再也选不回更宽的范围。

### 5.6.3 发布时间取哪个字段（跟实体类型有关）

实测 400 篇抽样：

| entityType | 形态 | 创建时间字段 | 占比 |
|---|---|---|---|
| 74 | 动态 `/feed/main/detail/…` | `createdAt` | 64% |
| 8 | 讨论 `/discuss/…` | `createTime` | 28% |
| 73 | 题解 | `createTime` | 8% |

三类都另有 `editTime`（最后编辑时间）。原来只读 `createdAt`，
于是 `/discuss/` 那批（36%）**全部落到 `editTime` 兜底**——
存的是最后编辑时间，被编辑过的帖子日期会偏晚（实测 21 篇偏晚，最多差一周）。

修法是按 `createdAt → createTime → editTime` 依次取值，
回归测试 `TestCreatedAtPrefersEntitySpecificField`。
**这个问题只在做时间筛选时才会暴露**：不按时间看，日期偏几天没人注意。

### 5.7 转帖闸门：频次必须按「独立内容」算

**现象**：按频次排序的 Top 榜上出现一整段计数完全相同的题——76× 的 4 道、
57× 的 22 道，且集中在同一批前端/美团方向。真实语料里不会有这么多题精确并列。

**定位**：把 22 道 57× 的题的来源帖子全拉出来，1,254 条出现记录
**100% 来自标题含「内推」的帖子**。点开正文就是一份内推广告 + 一整份「模板面经题单」：

```
美团内推来啦！欢迎大家用我的码社招&实习都可以用
美团内推链接（手机端）：https://zhaopin.meituan.com/...
以下是面经分享：
第一轮技术面
自我介绍
强缓存与协商缓存机制实现原理
...
```

**不是 57 个人真的考过这 22 道题，而是同一份模板被贴了 57 次。**

#### 为什么现成的广告规则在这里失效

`IsRecruitAd` 的判据是「有强广告词 且 面试信号 < 2」。而这类广告**自己带着一整份题单**，
题单里的「一面 / 自我介绍 / 手撕」把面试信号刷满，于是被判成真面经。
量级上也不能一刀切：178 篇这类帖子贡献了 **3,927 条有效题记录（占全部有效频次的 22%）**，
当广告删掉会连题一起删。

#### 判据：同标题 + 题集高度重合

问题不在「它是不是广告」，而在**重复计数**。所以闸门设在计数这一层：

```
归一化标题（只留字母/数字/汉字）相同
  且
题目集 Jaccard 相似度 >= 0.8        （-dedup-thresh，默认 0.8）
```

只保留每组里 id 最小的一篇，其余连出现记录一起删掉，再按 `occurrences`
重算 `questions.n` 并清掉 `n=0` 的簇。

试过更弱的口径，都不够：

| 口径 | 结果 |
|---|---|
| 正文指纹（去 URL、去数字） | 各人的内推码是**字母**，归一化不了，最大组只有 9 篇 |
| 题目集**完全相同** | 只能收回一半（76×→47×），模板之间还会多一两条 |
| **同标题 + Jaccard ≥ 0.8** | 假并列清零，有效题一道没少 ✅ |

#### 实测效果

| | 修前 | 修后 |
|---|---|---|
| 第 1 名 | 自我介绍 192× | 自我介绍 178× |
| 第 2 名起 | 76× ×4、57× ×22（全为同一份模板） | 19×、19×、15×、13×、13×、13×、12×…（Redis 分布式锁、进程与线程、TCP/UDP、事务隔离级别、MVCC） |
| 并列 57 的簇 | 22 个 | 0 个 |
| 删除帖子 | — | 409 篇（19%） |
| 有效题 | 17,684 | 17,684（**一道没少**，消失的 55 个簇全是「非题目」） |

#### 实现与注意事项

```bash
bin/nc-parse -classify -prune            # -dedup 默认开
bin/nc-parse -classify -prune -dedup=false   # 需要看原始频次时关掉
```

- 代码：`internal/store/dedup.go`（`NormalizeTitle` / `jaccard` / `DuplicatePostIDs` /
  `DeduplicatePosts`），闸门挂在 `cmd/parse` 重建聚类之后、清空帖之前。
- **必须每次 parse 都跑**：`parse` 会把 raw 里所有页面**重新灌一遍**
  （包括上一轮删掉的转帖），所以闸门是幂等收敛的——同一轮内先灌后删，终态一致。
- 判据里特意保留「题目集」这一条：**光看标题会误杀**。
  两个不同的人写《字节一面面经》是正常的，题集不重合就不该删。
- 回归测试：`TestDuplicatePostIDsCollapsesReposts`（同题集必删、同标题异内容不删）、
  `TestDuplicatePostIDsIgnoresEmptyTitleAndEmptyQuestions`、
  `TestDeduplicatePostsCollapsesRepostsAndKeepsQuestions`（真连库：删帖后频次回落且不丢题）。

> ⚠️ **`parse` 现在要跑 10 分钟以上**（13,000+ 原始页 → 重建 5 万行聚类 → 去重 → 清空帖）。
> 前台命令行的 10 分钟上限会把它掐断；**用后台任务跑**，并且被掐断也不会丢数据
> （标注按 `norm` 存在 `llm_labels`，重建中断后重跑即可）。

#### 跨标题洗稿：补第二条判据

只靠「同标题」会漏掉一批**换了标题的同一份内容**：

```
[迅雷内推，迅雷面试经验分享，可礼貌取码] ≈ [迅雷内推码分享，迅雷服务器开发面经]   J=1.00
[合合信息测试实习面经，合合信息内推]     ≈ [合合信息面经，合合信息内推分享]       J=1.00
[快手数据研发面经，快手内推，现在校招和实习都有hc] ≈ [快手数据研发面经，快手内推，今年校招无笔试] J=1.00
```

所以补了第二条：**两边题目集都 ≥8 且有 ≥0.9 的 Jaccard**。

**为什么必须加「最小 8 题」**：题集小的时候 Jaccard 完全不可靠——两篇各 4 道题、
恰好重合 4 道就是 1.0。实测不设下限时有 151 对，其中 44 对两边都不带「内推」，
一看全是小帖误配：

```
J=1.00  【社招复盘】面试，是人类讲故事能力的巅峰炫技 ≈ 嵌入式经典百套大厂面试题总结   （各 4 题）
```

加上「最小 8 题」后剩 109 对，其中 95 对含「内推」，其余是上面那种同内容换措辞标题。
实现在 `internal/store/dedup.go`：先做同标题那一遍，再用**只装保留帖的倒排索引**
做第二遍，边扫边建，天然保证「留 id 更小的那篇」。
剪枝条件用 `c*19 >= 9*(li+lj)`（J≥0.9 的必要条件），注意**不能**写成
`c >= 0.9*max(li,lj)`——那个条件过强，会漏掉大小不等的对。

回归测试：`TestDuplicatePostIDsCrossTitleReposts`、
`TestDuplicatePostIDsKeepsTinySetsApart`、`TestDuplicatePostIDsCrossTitleNeedsHighOverlap`。

#### 残留边界

**改写了内容的洗稿**（同一场面试换措辞重写、题目也重新表述）仍会算多次，
要再收敛得做语义级去重（把题目文本向量化后聚类），目前没做。

### 5.8 同义题合并：让频次落在「同一道题」上

同一道题的不同问法会被字符串聚类拆开：

```
390× 自我介绍一下。  55× 请简单介绍一下自己  52× 请做一下自我介绍。  19× 1️⃣自我介绍  …
19× 介绍一下你的项目  10× 你之前的项目实现了什么功能？  8× 拷打-- 项目  6× 项目拷打  …
```

对「按频次排序」来说这是直接失真：榜首那道题的真实频次是 626，列表上却显示 390。

**做法**（三步，全部可复核）：

1. 只取 **n≥3 的 760 个簇**——它们决定榜单形状，n=1 的三万多个簇合并不影响任何排序；
2. 让模型提出**同义组**候选（4 个分片并行），要求「宁可不合并，也不要错合并」；
3. **人工逐组复核**，剔除 5 组判错的，例如
   `redis为什么快？` ≈ `热点商品读多写多，仅靠本地缓存能否解决？`（不是同一个问题）、
   `你为什么选择我们公司？` ≈ `你为什么选择这个岗位？`（选公司与选岗位是两回事）。

**必须做两轮。** 第一轮只在「组内」合并，组与组之间并没有比过，于是
「自我介绍」这一件事会留下 6 个各自合并过的簇（552× / 28× / 23× / 8× / 5× / 4×）——
榜首那道题的真实频次是 600+，列表上却显示 552。所以第二轮只把这 **79 个组代表**
拿出来再判一次（12 组 / 99 条），把它们之间也是同义的并掉。

产出 `data/llm/merges.json`（91 组 / 143 条映射），由 `importer.LoadMerges` 读入，
在**聚类前**把每条行的 norm 映射到合并目标的 norm，于是同义问法自然落进同一簇——
后续的频次、公司覆盖面、大模型标注全部沿用原有管线，不需要额外改造。

> ⚠️ **合并必须同时把代表措辞钉在合并目标上**（`cluster.forceRep`）。
> 否则整簇最终的代表措辞仍是簇内最长的那条变体，`norm` 就不等于合并目标，
> 而大模型标注是**按 norm 存**的（`llm_labels`）——合并后的整簇会**静默丢掉标注**。
> 这个不变式由 `TestClusterMergeKeepsNormInvariant` 钉住。
>
> ⚠️ **链式映射必须解析到不动点**。第二轮会产生 A→B、B→C 这样的链，
> 单层查表会把 A 归到 B，而 B 的簇已经并进了 C——A 变成一个只有自己的孤簇，
> 频次一起丢掉，而且**不报错**。`LoadMerges` 因此会把每条映射解析到最终目标，
> 并删掉自环。回归测试 `TestLoadMergesResolvesChains`。
>
> 另：`LoadMerges` 在文件不存在时返回空映射，行为与「没有合并」完全一致，
> 便于冷启动与测试（`TestLoadMergesMissingFileIsNoop`）。

## 十三、全站抓取：产出率、空壳页与并行策略

### 目标

从 sitemap 的 **26,623 条** URL 里抓面经，把数据从最早那一个用户的公开动态
扩到「多用户、多公司、多岗位、多轮次」。这是整个项目从「个人面经本」
变成「面经库」的关键一步——也是唯一一步需要长时间跑的。

### 实测产出率（决定性数字）

抓了 **6,681** 条原始页之后的累计漏斗：

| 阶段 | 数量 | 每 100 页 |
|---|---|---|
| 抓取原始页 | 6,681 | — |
| 通过粗筛入库的帖子 | 1,168 | **17.5 篇** |
| 抽出的问题簇 | 16,105 | **241 组** |
| 其中有效题（模型未判为非题目）| 9,525 | **143 组** |
| 其中带参考答案的题 | 3,774 | **56 组** |

另有 97 篇来自个人时间线（不是 sitemap 路径），355 篇带官方结构化真题。

**换算成一句话**：抓 100 条 URL 大约得到 **17 篇面经 / 143 道有效题 / 56 道带答案的题**。

这条产线里最有性价比的是官方结构化真题：它只出现在 **约 4%** 的页面上，
但每篇平均带 11 道题且**全部附参考答案**——按全站推算约 1,100 篇帖子、
1.2 万道带答案的题（见 5.6）。

### 实测产出率（早期估算，已被上面的实测取代）

531 条原始响应的漏斗：

| 阶段 | 条数 | 占比 |
|---|---|---|
| 抓取落盘 | 531 | 100% |
| 解析成功 | 531 | 100% |
| 通过粗筛 | 142 | 26.7% |
| 其中**带官方结构化真题** | 23 | 4.3% |

噪声构成（粗分类）：

| 类别 | 占比 |
|---|---|
| 内推/招聘广告 | 43% |
| 疑似面经 | 25% |
| 其他闲聊 | 21% |
| 题解 | 7% |
| 空内容（打卡动态） | 4% |

**关键结论：内推广告是最大的单一噪声源（43%）**，比真面经还多。
`/feed/` 与 `/discuss/` 两类 URL 的产出率几乎一样（23.6% vs 28.0%），
所以**不需要按类型分流**——早先 21 条样本得出的「/feed/ 好得多」是小样本噪声。

### 为什么抓 26,623 条不是 26,623 次「有用请求」

- 主站内容分 `/feed/`（16,163）与 `/discuss/`（9,856）两类，**结构完全一致**，
  都走 `prefetchData.2.ssrCommonData.contentData`，不需要写两套解析。
- 大量内容是题解、内推广告、打卡动态、闲聊——噪声闸（见 5.2 / 5.5）砍掉约 73%。
- 所以**抓取成本远大于入库成本**：落盘的是 26,623 份 HTML，最终入库的只有约四分之一。
  这正是「落盘优先」的意义——原石留着，判据改了不用重抓。

### 空壳页：200 不等于拿到内容，而且它不是限流

牛客至少有**三种**「HTTP 200 但不是内容」的返回，都必须识别：

| 变体 | 体积 | 特征 |
|---|---|---|
| ① 骨架页 | 约 6KB | 只有 `<head>`，完全没有 SSR 数据 |
| ② 兜底页 | 约 82KB | `contentData` 存在但是**空对象 `{}`**（实测 5 条，内容全同） |
| ③ 空正文但带 uuid | 130KB+ | **合法**的打卡动态，要留下 |

不识别的话会把空壳当成功结果永久落盘，
而且 `Has()` 判重会让这个 URL **再也不会被重抓**。

> ⚠️ **判据必须是语义的，不能查子串。** 早先只检查正文里是否出现 `"contentData"`
> 这个字符串，于是变体 ② 被当成有效内容页落盘，在解析阶段变成一条
> title/content/uuid 全空、日期 1970 的脏数据——而它**通过了所有抓取侧检查**。
> 现在 `LooksLikeContentPage` 会真的解出 contentData 并检查它是否带身份标识
> （`uuid` 或 `id`）。代价是每个响应多一次 JSON 解析（1~2ms），
> 相对 500ms 的网络耗时可以忽略。

#### 它是「时间窗口」，不是「限流」，也不是「URL 坏了」

这三者的应对方式完全不同，所以花了几个实验来区分：

| 观察 | 结论 |
|---|---|
| 空壳 0.1~0.2s 返回，内容页要 0.6~0.7s | 快说明是「没渲染」，不是「被拦后惩罚」 |
| 完全静默 2 分钟、**零并发**、5s 间隔慢速探测，仍有 25% 空壳 | 与请求频率无关 → **不是限流** |
| 同一个 URL 连打 5 次全是空壳；12 秒后同样连打 6 次全是内容页 | 与 URL 无关 → **不是链接失效** |
| 侧信道另开全新会话（无 Cookie）请求，同样拿到空壳 | 不是本地会话被烧 |
| 坏窗口里**所有** URL 都是空壳 | 是**站点级的、按时间切换的状态** |

所以空壳的模型是：站点在「正常服务」和「只发空壳」两种状态之间切换，
坏窗口持续几秒到几分钟。**坏窗口里快速重试是白费请求，正确做法是停下来等。**

#### 三道处理，以及一个代价很大的错误

1. **抓取阶段识别**：`LooksLikeContentPage` 检查正文是否含 `contentData`；
   不含则按可重试失败处理，**不落盘**。
2. **就地重试**：`-tries 3`，间隔 `-shell-wait`（默认 1.5s，1~2 倍随机）。
3. **事后复核**：`make fetch-check` 扫描已落盘数据，删掉空壳并重写清单，
   被删的 URL 自动重新排队。用于清理「识别逻辑上线之前」落下的脏数据。

> ⚠️ **踩过的坑：把空壳当成「站点在拒绝我们」，于是给了 10 秒指数退避。**
>
> 后果是吞吐被拖垮近 **7 倍**：单请求均耗时从 0.5s 抬到 4.5~8s，
> 整体从 0.71 条/秒掉到 0.11 条/秒。而且因为重试最终会成功，
> 日志里只看到「失败 0」，问题完全不可见——是给进度行加上
> 「单请求均耗时」这个指标之后才暴露出来的。
>
> **教训：退避是给「对方在拒绝你」用的。空壳是「这次没渲染」，
> 惩罚性等待只会惩罚自己。** 判断错误类型比设置等待时间更重要。

### 并行抓取：分片 + 跨进程断路器

单线程太慢（实测 0.12 条/秒，跑完 26,623 条要 60 小时以上），
所以改成 **多进程分片并行**（当前 4 片）。

**分片按 URL 哈希取模，不按下标切片**（`-shard i/N`）：

```
ShardOf(url, i, n) = sha1(url)[:8] % n == i
```

按下标切片会让同一个 URL 在不同轮次落到不同分片（sitemap 顺序会变，
站点随时新增内容），于是「本分片已抓完」这个判断失效。
哈希取模对同一个 URL 恒定，且天然是**划分**（每个 URL 恰好落进一片），
不会漏抓也不会重复抓。有测试钉住这两条性质。

**跨进程断路器**（`data/raw/_breaker.json`）：

单个进程的退避救不了整体——站点开始软限流时，三个 worker 会各自
「礼貌地」降速，但合起来仍在持续敲门。断路器用一个共享文件把
「现在该停」广播给所有进程：任一 worker 判定异常，就写入「冷却到 T」，
其余 worker 每次请求前读这个文件，到点之前一律等待。

- 写入用 `rename` 保证原子，避免读到半截 JSON
- 冷却取「更晚的那个截止时间」，不缩短已有冷却
- 冷却时长**逐次翻倍**（60s → 10min 封顶），连续拿到内容页后自动回落

**用窗口比例而不是「连续 N 次」判定异常**：空壳是概率性的（实测 25%~50%），
若单次概率 0.5，连续 3 次的概率高达 12.5%，用它当限流信号会频繁误触发。
按最近 16 次的比例判断，才能把「偶发」和「持续」分开。

### 落盘要原子：抓取与解析是并行的

`make parse` 常年与抓取进程并行跑。`Save` 若直接 `os.Create` 目标文件，
读者会看到**写了一半的 gzip**——表现为 parse 报若干条「解析失败」，
重跑就好。这种偶发错误最难查，所以改成「先写临时文件再 rename」。
`rename` 在同一文件系统内是原子的，读者要么看到旧文件、要么看到完整的新文件。

#### 分片数不是越多越好：实测过一次拐点

| 配置 | 名义速率 | 断路器触发 | 实测**有效**速率 |
|---|---|---|---|
| 1 片（含 10s 空壳退避）| — | — | 0.12 条/秒 |
| 4 片，2~5s | ~0.9 请求/秒 | 偶发 | 0.55~0.65 条/秒 |
| 8 片，2.5~6s | ~1.9 请求/秒 | **频繁**（单分片失败数涨到 10~16）| 0.56~0.71 条/秒 |
| **6 片，3~7s + 更长休息** | ~1.2 请求/秒 | 很少（单分片失败 0~3）| **0.75 条/秒** |

**8 片反而比 6 片慢。** 名义吞吐翻倍了，但断路器频繁介入（冷却 60s 起、逐次翻倍），
把多出来的吞吐又吃回去了；同时站点的失败数明显上升。

所以分片数应该定在**「断路器基本不触发」的最大值**，而不是能开的实际最大值。
这个拐点要看两个信号：单分片失败数、断路器触发频率——两个都在涨就说明过头了。

### 时间估算与实测

按 0.65 条/秒，8 小时约 **1.9 万条**——接近全站 26,623 条的 70%。
但站点状态会波动，实际以日志为准；断路器触发时速率会掉下来，这是设计内行为。

### 运维流程（每批一次）

```bash
make fetch-dry                  # ① 看队列
make crawl SHARD=0/4 MINUTES=240   # ② 常驻抓取（崩溃自动重启、到点自停）
make fetch-check                # ③ 复核：删空壳，URL 重新排队（⚠️ 需先停抓取）
make parse-only                 # ④ 入库（不重建聚类，快）
make rebuild                    # ⑤ 重建聚类
make llm-apply                  # ⑥ 保留已有 LLM 标注
# ⑦ 新数据跑 LLM 归类（三步解耦，见 5.3）
```

**注意顺序**：`make parse` 会顺带 `-classify -prune`，数据量大时建议先
`parse-only` 确认入库条数正常，再单独 `rebuild`——因为 `rebuild` 是全局操作，
出问题不好回滚。

⚠️ `make fetch-check` 会**重写清单**，必须在抓取停止时跑；与并行抓取同时跑会丢记录。
其余操作（parse/rebuild）读的是清单和原始文件，与抓取并行是安全的。

### LLM 归类的规模问题

全量入库后约有 **2 万条问题行**。按 150 条/批需要约 **130 个批次**。
三步解耦让这件事可控：分批归类的结果落在 `data/llm/out/`，
合并在 `merge.json` 里做，**合并不消耗模型调用**。

### 尚未解决 / 需要决策的点

1. **内推广告占 43%**：目前只能在解析侧丢弃，仍需先花带宽抓下来。
   是否值得在建索引阶段（先抓首页/列表页判断类型）就排除？
2. **`entityType` 白名单**：已观测 `74`（动态）、`8`（讨论）、`73`（题解）。
   在解析侧过滤是免费的，但省不了抓取成本。
3. **多用户溯源**：同一道题被 500 篇面经提到，是「高频」还是「同一批人抄的」？
   当前用 `occurrences` 计数，未做来源独立性分析。
4. **官方真题的覆盖率上限**：`experienceQuestionList` 只在 4.3% 的帖子上有，
   且这部分帖子题量是自动抽取的数倍——是否值得按「有无真题」给抓取排优先级？
