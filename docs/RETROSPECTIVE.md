# 全站面经抓取：复盘

> 本文回答一个目标：**从牛客 sitemap 持续抓取面经并扩充题库**——做到了什么规模、
> 单位抓取产出多少、期间踩过哪些坑、每个坑是怎么修和怎么验证的。
>
> 数据截至全站抓取收工（**25,927 / 26,623 条 URL，97.4%**）后。持续抓取的与数据清洗的细节见
> `DEPLOYMENT.md`；本文只讲结果、结论与教训。

## 二、遇到的 9 个问题

按影响面排序。每个都配了回归测试。

### 1. 一行里连排了几十道题（最大的一次召回缺口）

**现象**：248 条题目的长度**正好等于 1000**——那是列宽上限。捞出来看：

```
Java 基础 == 和 equals 的区别？hashCode 为什么要一起重写？String 和 StringBuilder 区别和使用场景？…
请做一下自我介绍。你的专业偏开发，为什么选择测试开发岗位？你对测试开发岗位有什么了解？…
```

**根因**：不少帖子把题目**连排在一段里、没有任何换行**。逐行抽取时整段只算一行，
几十道题被当成一道。其中一份「高频面试题清单」一段就含着 50 多道题。

**修法**：`splitInlineQuestions`——长度 >40 且问号数 ≥2 时在每个问号后切一刀。

**效果**：问题簇 20,631 → **22,130**；被截断的题 248 → **0**；
某篇「B站测试开发一面」从产出 1 道变成 **32 道**。

### 2. 聚类锚点漂移导致链式吞噬

**现象**：一个簇吃掉了 **2,063 个变体、360 次出现**，成员从「智能指针」到
「agent runtime」到「YUV 格式」毫无关系；其余簇最大只有 60。

**根因**：合并判据用了会变的 `g.norm`（取簇内最长那条的归一化文本，随成员加入而变长），
再叠加 `strings.Contains` 与「并入第一个匹配簇」的单链接策略，就成了链式吞噬。

**修法**：合并只用**进簇第一行的锚点**（永不改变）+ 包含关系的**长度比上限 2 倍**。

**效果**：最大簇 360 → **60**；有效题 4,957 → **7,111**（+43%）。

### 3. `company == ""` 静默丢弃真面经

**现象**：13 篇「一条题都没抽出来」的帖子里，6 篇是真面经
（`上海某量化开发 一面`、`遥望科技 hr面`、`转转 FDE 线下面试`）。

**根因**：抽题入口用 `p.Company == ""` 判断「不是面试帖」，而 `company` 来自
「公司 岗位 轮次」这个严格格式。标题只有一个空格就解析不出来，
于是真面经和「打卡动态」在库里长得**一模一样**。

**修法**：判据换成「标题里有没有面试信号」。

**效果**：问题 1,478 → **1,576**；真正空的帖子 13 → **4 篇**。

> 这个坑最危险的地方：如果当时直接跑「清理空帖」，**删掉的就是真数据**。

### 4. 标注随失败的重建一起消失 / 按 id 落地会静默贴错标签

**现象 A**：一次重建因列宽报错中途失败——TRUNCATE 已执行、写回没跑，
**1,477 条模型标注全部丢失**。
**现象 B**：恢复时按 id 重新 apply，而 id 是重建后重排过的自增主键，
于是 1,478 条标注被贴到无关题目上，**实测匹配率 0/212**，而且不报错。

**修法**：标注单独存 `llm_labels` 表，主键是**题目归一化文本**（稳定键），
`questions.llm_*` 只是物化视图；批次文件必须带 `text`，缺 text 的结果拒绝导入。

### 5. 空壳页被误当成「站点在拒绝我们」

**现象**：抓取速率 0.11 条/秒，单请求均耗时 4.5~8 秒。

**根因**：200 状态但只有 6KB 骨架的空壳页，我当成了限流并给了 10 秒指数退避。
做了几个实验才定性它是**时间窗口**：静默 2 分钟、零并发、5s 间隔慢跑仍有 25% 空壳；
同一个 URL 连打 5 次全空壳，12 秒后连打 6 次全内容页。

**修法**：空壳不进退避、就地快速重试；坏窗口用**跨进程断路器**让所有分片一起停。

**效果**：0.11 → **0.75 条/秒**（6.8×）；单请求 4.5~8s → **0.5s**。

> **退避是给「对方在拒绝你」用的。空壳是「这次没渲染」，惩罚性等待只惩罚了自己。**

### 6. 分片数不是越多越好

**现象**：4 片 → 8 片后名义吞吐翻倍，但断路器频繁触发，**有效速率反而下降**。

| 配置 | 名义请求速率 | 断路器 | 实测**有效**速率 | 单分片失败数 |
|---|---|---|---|---|
| 4 片 | ~0.9/s | 偶发 | 0.55~0.65 条/秒 | ~3 |
| 8 片 | ~1.9/s | 频繁 | 0.56~0.71 条/秒 | 10~16 |
| **6 片** | ~1.2/s | 很少 | **0.75 条/秒** | 0~3 |

**结论**：分片数应定在「**断路器基本不触发的最大值**」，而不是能开的实际最大值。

### 7. `__INITIAL_STATE__` 正则截断

**现象**：66 条样本里 1 条报 `unexpected end of JSON input`。

**根因**：用 `(\{.*?\});` 提取 SSR JSON，而 `.*?` 会在**字符串字面量内部**的 `};`
处提前收尾——面经正文经常内嵌代码，受影响的恰恰是算法/手撕类帖子。

**修法**：改成花括号配对扫描（跳过字符串与转义）。

### 8. 公司词典的自我强化污染

**现象**：库里长出 `Coding`（7 篇）、`0904`（日期）、`27Shoppe` 这些假公司。

**根因**：三层叠加——① ASCII 名字用裸 `strings.Contains` 匹配，`coding` 命中了
`aicoding`；② 「猜」这条路会把通用技术词（Infra / Agent / Platform）当公司名；
③ **词典是从库里学来的，坏名字一旦进库下次回填又会被应用回来，永远清不掉**。

**修法**：ASCII 名字卡词边界；通用技术词停用表；纯数字只认种子表；
**学来的名字也要过筛**。

### 9. 三次「同名不同义」的 SQL 层错误

都是编译通过、单元测试通过、只有真库才报的：

- `ON DUPLICATE KEY UPDATE ... IF(new.x='', x, new.x)` 里裸列名被判 ambiguous，
  **所有新帖插入静默失败**（日志只有一行写入失败）；
- `answer` / `official_q` 是 NULL，`Scan` 进 string 报错，让**整个问题列表**挂掉；
- 官方真题是完整句子，撑爆 `norm` 的列宽。

**修法**：修 SQL + 补上**真连 MySQL 的集成测试**（`internal/store/store_test.go`）。
纯函数测不出 SQL 层的错误——这组测试专门为此而建，它当场就抓出了上面第二、三条。

### 10. 转帖把模板题单刷成了整齐的假频次

**现象**：按频次排序的 Top 榜上出现了一整段计数完全相同的题——
76× 的 4 道、57× 的 22 道，而且高度集中在同一批前端/美团方向。
真实语料里不可能有这么多题精确并列。

**定位**：把 22 道 57× 的题的来源帖子全部拉出来，1,254 条出现记录
**100% 来自标题含「内推」的帖子**。点开一篇正文是这样：

```
美团内推来啦！欢迎大家用我的码社招&实习都可以用
美团内推链接（手机端）：https://zhaopin.meituan.com/...
以下是面经分享：
第一轮技术面
自我介绍
强缓存与协商缓存机制实现原理
...
```

内推广告把同一份「模板面经题单」连同自己的内推码复制了几十上百遍。
**不是 57 个人真的考过这 22 道题，而是同一份模板被贴了 57 次。**

**为什么广告规则在这里天然失效**：`IsRecruitAd` 的判据是「有广告词 且 面试信号 < 2」，
而这类广告**自己带着一整份题单**，题单里的「一面／自我介绍／手撕」直接把面试信号刷满，
于是被判成真面经。更麻烦的是量级：178 篇这类帖子贡献了 3,927 条有效题记录
（占全部有效频次的 **22%**），所以也不能一刀切当成广告删掉——那会连题一起删。

**修法**：问题不在「它是不是广告」，而在**重复计数**。改成按题集去重：

- 归一化标题（只留字母、数字、汉字）相同，**且**
- 题目集 Jaccard 相似度 ≥ 0.8

只保留每组里 id 最小的一篇，其余删掉，再按 `occurrences` 重算 `questions.n`。
（实测过更弱的口径：只按正文指纹去重会漏——各人的内推码是字母，去掉数字也归一不了；
只按题目集完全相同去重也只能收回一半，因为模板之间还会多一两条。）

**效果**（全量实测）：删掉 **409 篇转帖（19%）**，**有效题一道没少**
（消失的 55 个簇全部是「非题目」），Top 榜从整齐的假并列变回真实分布：

| | 修前 | 修后 |
| --- | --- | --- |
| 第 1 名 | 自我介绍 192× | 自我介绍 178× |
| 第 2 名起 | 76× ×4、57× ×22（全为同一份模板） | 19×、19×、15×、13×、13×、13×、12×…（Redis 分布式锁、进程与线程、TCP/UDP、事务隔离级别、MVCC） |
| 并列 57 的簇 | 22 个 | 0 个 |

对应实现：`internal/store/dedup.go`，闸门挂在 `parse -dedup`（默认开，`-dedup-thresh` 可调），
测试 `TestDuplicatePostIDsCollapsesReposts`（同题集必删 / 同标题异内容不删）、
`TestDeduplicatePostsCollapsesRepostsAndKeepsQuestions`（真连库：删帖后频次回落且不丢题）。

**教训**：**频次是「有多少篇独立内容提到」，不是「有多少行文本匹配」。**
在按频次排序的产品里，重复内容不是「稍微不准」，而是**直接把排序结果变成假的**；
而这件事光看题目内容完全看不出来——只有把「这个计数是从哪来的」拉出来看才会暴露。
这和问题 2（聚类锚点）是同一类：**看的指标对了，但统计的总体不对。**

### 11. 我自己引入的一次「提升覆盖率」回归：正文兜底把八股合辑整篇标错

**背景**：面试轮次是用户明确要的筛选维度，但只有 51% 的帖子能从标题认出轮次。
于是加了一条兜底——标题认不出时，从正文认。

**第一版规则**：正文里**任意位置**出现轮次词，且恰好只出现一种 → 采用该轮次。
覆盖率「提升」很明显：多标 129 篇 / 1,544 道有效题，一面题数 4,598 → 7,795。

**但这个提升是假的。** 抽查标注结果时看到：

```
[一面] 嵌入式CAN总线必备八股文总结         40 题
[一面] 软件测试基础50道大厂高频面试真题     53 题
[一面] 字节面经-字节跳动后端开发岗面经-07   104 题
```

回正文看命中位置：

> 「熬了好几个夜啃自动化框架、性能调优……结果**一面**开场 10 分钟，就栽在了基础题上。」

是**叙述性提及**，不是轮次标题。一份通用八股合辑只因为在开头讲了个故事提到「一面」，
整篇 40~104 道题就被算进了「一面」这个筛选项——用户按「一面」筛，筛出来的是错的。

**修法**：只认**标题式行**——整行 ≤24 字，且按「轮次键」归一
（一面/第一轮=1、二面/第二轮=2、三面=3、终面=5、HR面=hr）。
出现两种以上键（帖子横跨多轮）就留空。

同一批数据：129 篇 / 1,544 题 → **20 篇 / 279 题**，剔掉的 122 篇正是那些叙述性提及。
**用键而不是名字比较是关键**：正文同时有`第一轮技术面`和`第三轮HR面`的帖子，
键是 {1,hr}，单看正文判断不了某道题属于哪一轮——留空比标错好。

**教训**：**补召回的时候必须同步量精确率**，否则「覆盖率提升」可能只是在把错的标得更多。
这次只看「多标了多少题」，会得出与事实完全相反的结论。
（这是同一个模式的第三次出现：指标算对了，但**统计的总体**或**判据的强度**不对——
见问题 2 的「用 canonical 量、却把规则跑在 raw line 上」，和问题 10 的「同一份模板被算了 57 次」。）

### 12. 聚类热路径：30 亿次 `[]rune` 转换，一次重建跑一小时进不到写库

**现象**：全站抓完后，一次 `parse`（重建聚类）从 43 分钟涨到 **60 分钟以上还没结束**，
卡在「重建问题聚类…」这一步，MySQL 里一条活动查询都没有——说明瓶颈不在数据库。

**定位**：看热路径，聚类是「行数 × 簇数」的单链接扫描
（10 万行 / 6 万簇 ≈ **30 亿次比较**）。而内层循环写的是：

```go
for i := range cs {
    g := &cs[i]
    la, lb := len([]rune(g.key)), len([]rune(n))   // ← 每次比较都做两次转换
    ...
    if ... || Similar(n, g.key) >= similarThreshold {   // ← 几乎每对都跑完整 Levenshtein
```

三个问题叠在一起：

1. `la`、`lb` 与 `g` 无关，却被放在循环里，每次比较都分配两个 `[]rune`；
2. `Similar` 内部还会再转两次 `[]rune`，等于每对 4 次分配；
3. `Similar` **没有长度剪枝**，会把 `la×lb` 的 DP 表算完才返回——哪怕两条字符串毫不相干。

**修法**（每一步都用测试证明「结果不变」）：

| 优化 | 效果 |
|---|---|
| 长度提到循环外、`klen`/`krunes` 缓存在簇上 | 去掉每对的 `[]rune` 分配 |
| 加长度必要条件 | `Similar >= T ⇒ \|la-lb\| <= (1-T)·max`，超出直接跳过 |
| 带状 + 提前退出的 Levenshtein | 只算 `\|i-j\| <= maxD` 的格子 |
| DP 缓冲改栈数组 | 零分配 |

基准（2 万行）：**39.2s → 22.9s → 13.9s**；
端到端 `parse`：**60 分钟以上 → 3.5 分钟**（约 17×）。

**教训一：性能问题也要用「等价性测试」兜底，不能只看变快了。**
带状 DP 的第一版漏写了 `prev[hi+1]` 这个带外哨兵，复用缓冲区的残留旧值被当成
合法前驱，于是**毫不相干的两条字符串判成了相似**——聚类会因此大面积乱合并。
是 `TestSimilarAtLeastMatchesSimilar`（拿 6000 组随机样本，含相似/不相似/前缀/
等长不同四类，逐例对拍新旧实现）当场抓出来的。
**这类改动最危险的地方是「快是快了，但边界上偶尔判错」，而且不报错。**

**教训二：同一个数字（60 分钟）不值得直接接受，先问它花在哪。**
这次如果只是「等它跑完」，会白白多花一小时，而且下次还得再花。

### 13. 三分之二的「原文 ↗」跳到了空壳页

**现象**（用户报的）：点开题目里的「原文 ↗」，很多跳过去是空白页，例如
`https://www.nowcoder.com/feed/main/detail/816d2b9f19c24d3885155d6d8b77834f`。

**定位**：这个 URL 能打开、HTTP 200、页面里也有 `contentData`——**但不是这篇帖子**。
对照同一个内容 id 的另一种写法：

| URL | 打开后 |
|---|---|
| `/feed/main/detail/816d2b9f...` | 200，有 `contentData`，**搜不到标题里的「经纬恒润」** |
| `/discuss/922491544811098112` | 200，**正文就是「经纬恒润 \| 嵌入式软件 \| 一面」** |

再看抓取时用的 URL，sitemap 里写的是：

```
https://www.nowcoder.com/discuss/922491544811098112?urlSource=sitemap
```

**根因**在 `cmd/parse` 里一行想当然的拼装：

```go
pageURL := "https://www.nowcoder.com/feed/main/detail/" + p.UUID
```

`/discuss/<id>` 的帖子**同样带 uuid**，于是它们全被拼成了 feed 路径。
而 feed 路径对这类内容返回的是一张空壳页——200、有 `contentData`、没有正文，
所以**任何基于状态码或 `contentData` 的检查都发现不了**。

**影响面**：3,494 篇里 **1,270 篇**（36%）是 discuss 帖子；
按出现记录算，**44,817 条「原文」链接（64.4%）是坏的**。

**修法**：规范链接优先用**抓取时用的那个 URL**（它本来就是规范链接），
只在它不是内容页形态时才退回按 uuid 拼：

```go
pageURL := stripQuery(e.URL)
if !scraper.IsContentURL(pageURL) {
    pageURL = "https://www.nowcoder.com/feed/main/detail/" + p.UUID
}
```

**验证**：随机抽 3 篇 discuss + 3 篇 feed，逐个抓取并检查页面正文里**是否含标题**——
修复后 6/6 命中（修复前 discuss 那 3 篇全部搜不到标题）。
回归测试 `TestIsContentURL`。

**教训**：**「能打开」和「是同一个东西」是两回事。**
这次坏链全都返回 200、也都带 `contentData`，任何粗粒度的健康检查都会判它正常。
真正抓住问题的是「打开页面，看它**是不是这篇帖子**」——
和前一条（问题 12）一样：**指标本身没错，错的是它没测到真正要保证的性质。**

> 顺带记一个环境问题：修完之后重跑 `parse` 花了 **65 分钟**，但进程 CPU 时间只有
> **8 分钟**——其余时间卡在系统内存压力上（swap 用掉 6.2G/7.1G，pageins 2.4 亿次）。
> 也就是说「慢」的两次原因完全不同：问题 12 是代码，这一次是机器。
> 看 CPU 时间与墙钟时间的比例就能区分这两者。

## 三、几条可复用的做法

**① 拿模型标注反推规则。** 把模型判出的 10,424 条「非题目」当标注集，
逐个候选规则算精确率，**只采用 ≥92% 的**。上线效果：噪声簇 −318，有效题只 −2。
反例同样有价值：「含『为什么』但无问号」看着能拦 203 条，实际精确率只有 **9.4%**
（184 条是真问题）。

**② 异常值排查比抽样更有效。** 三次重大数据问题都是靠「看分布找断点」发现的：
最大簇 360 而第二名只有 61 → 聚类出错；248 条长度正好 1000 → 列宽截断；
4096 个 hash 却只有 3,477 行 → 并发写有丢失。**抽样看不出来，看分布一眼就能看出。**

**③ 量化验证再改。** 想加强广告关键词规则时，先用库内 432 篇数据算了一遍：
精确率最高只有 67%（要误伤 128 篇真面经），于是**放弃这条路**，
改用「有没有有效题」这个模型判定后的结论。
聚类改完也用全量两两比对验证过「没有引入新的拆散」（重复率 0.11%）。

**④ 回填必须自愈。** 标题字段的回填对**全部**帖子重算，而不是只补空字段——
否则解析规则修好后，旧的错误值永远纠正不了。

## 四、已知边界（未解决）

1. **噪声占比稳定在 ~40% 不再下降**：剩下的是攻略、面后感、广告、进度记录。
   规则层能拦的已经拦完（标注集涨到 10,424 条后，10 条候选规则只有 1 条过线），
   其余必须靠模型逐条判断。这是**这份语料的固有成分**，不是过滤没做好。
2. **183 条 >120 字的题**：把题目写成**没有问号的短语罗列**
   （`volatile关键字，是不是只用于多线程场景static修饰局部变量…`），
   没有任何分隔符可切，不再强拆。
3. **`company`/`round` 只覆盖一部分帖子**：公司 77%、轮次 26%——
   标题里本来就没写的信息，猜不出来。
4. ~~**`n`（频次）未做来源独立性分析**：同一道题被 500 篇面经提到，
   是「真的高频」还是「同一批人抄的」，目前无法区分。~~
   **已解决**：见问题 10。同标题转帖已按题集去重，假并列清零。
   残留：**换了标题的洗稿**仍会算多次，要再收敛得做语义级去重。
5. **全站抓到 97.4% 后按时间预算收工**：6 个分片各跑满 290 分钟（约 8h20m），
   合计成功抓取约 2.0 万条，剩 **696 条**没抓（分片是到时间预算停的，不是抓完了）。
   **这不是能力上限而是礼貌上限**——约 0.7~0.8 条/秒，再快会触发空壳页窗口反而更慢
   （见问题 5、6）。重跑 `scripts/crawl.sh` 即可续抓。
6. **服务无鉴权**，只绑 `127.0.0.1`；对外暴露前必须加认证。
