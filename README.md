# nc-interview

牛客面经的抓取、存储与多维检索。**Go 1.27 + MySQL 8.0 + 原生前端**，无框架、无 CGO、单二进制部署。

数据源：牛客网**公开面经**。最早从一个用户的公开主页时间线起步（10 万字量级），
现在主要靠全站 sitemap 抓取（26,623 条 URL）覆盖多用户、多公司、多岗位。
抓取策略与实测产出率见 `docs/DEPLOYMENT.md` 第十二节；
**完整的规模、产出率与问题复盘见 `docs/RETROSPECTIVE.md`**。

## 快速开始

```bash
# 1. 建库建用户（需要 MySQL root 密码，只新建 nc_interview，不动已有库）
#    先改 scripts/setup.sql 里的密码占位符（见下方「密码策略」）
mysql -u root -p < scripts/setup.sql

# 2. 配置连接（.env 已 gitignore）
cp .env.example .env && vi .env      # 填 NC_DB_PASS

# 3. 导入数据 + 建表（首次运行会自动应用 migration）
make import

# 4. 启动
make run          # → http://127.0.0.1:8787
```

浏览器打开 `http://127.0.0.1:8787` 即可。

### 密码策略（容易卡住的一步）

Homebrew 的 MySQL 默认启用 `validate_password`，策略为 **MEDIUM**，要求：

> 长度 ≥ 8、**含大写**、**含小写**、**含数字**、**含特殊字符**，且**不能包含用户名**。

不满足会直接报 `ERROR 1819 (HY000): Your password does not satisfy the current policy requirements`。
纯随机字母数字（即使 24 位）也会被拒——**必须带特殊字符**。

```sql
SHOW VARIABLES LIKE 'validate_password%';   -- 查看当前策略
```

另外，DSN 里的密码建议只用这些特殊字符，免得转义或 shell 引号出问题：

```
%  *  +  -  =  ^  _
```

（避开 `@ / : ? # ! $ \ " ` 和空格——`@` 会干扰 DSN 的凭据/地址切分，`!` 在交互式 shell 里会触发历史展开。）

### 配置来源

全部走环境变量，也支持项目根目录的 `.env`（环境变量优先）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `NC_DB_USER` | `nc_app` | 数据库用户 |
| `NC_DB_PASS` | 无 | 密码（**必须设**） |
| `NC_DB_HOST` | `127.0.0.1:3306` | 地址 |
| `NC_DB_NAME` | `nc_interview` | 库名 |
| `NC_DSN` | — | 完整 DSN，设了就覆盖上面四项 |
| `NC_ADDR` | `127.0.0.1:8787` | 监听地址 |
| `NC_WEB` | `web` | 前端目录 |
| `NC_USER_ID` | `125006155` | 目标牛客用户 |
| `NC_COOKIE` | 无 | 仅在线抓取需要 |

日志里会打印**脱敏后**的 DSN（`nc_app:****@tcp(...)`），密码不会进日志。

### 在线抓取（需要 Cookie）

动态列表接口要求登录态，Cookie **只从环境变量读取，不落盘**：

```bash
NC_COOKIE='你的完整 Cookie 头' make scrape
```

Cookie 获取方式：浏览器登录牛客 → F12 → Network → 任意请求 → 复制 `Cookie` 请求头的完整值。

### 全站面经抓取（免登录）

个人时间线只能拿到一个用户的帖子。要扩充到多用户/多公司/多岗位，
走牛客**主动发布**的 sitemap（`robots.txt` 声明的爬虫入口），全程免登录：

```bash
make fetch-dry     # 先看队列（26,623 条），不发请求
make fetch         # 抓 500 条：随机 1.5~4s + 每 30 条长休息；Ctrl-C 可中断
make fetch-check   # 复核：删掉空壳页，被删的 URL 重新排队
make parse-only    # 原始 HTML → posts 表
make rebuild       # 重建聚类
make parse         # 或一步到位：入库 + 重建聚类 + 清理空帖（-classify -prune）
```

抓取与解析**刻意分离**：原始响应 gzip 落在 `data/raw/`，按 URL 哈希去重。
解析规则（提取路径、粗筛阈值）改了就重跑 `make parse`，**不必重抓**——
分类判据一定会改很多次，原始数据只该抓一次。

三个容易踩的点（详见 `docs/DEPLOYMENT.md` 第五节）：

- **200 不等于拿到内容**：牛客会间歇性返回约 6KB 的空壳页，
  同一 URL 隔几秒重试就恢复。抓取器会识别并重试，不会把空壳当成功结果落盘。
- **`createdAt` 可能是 `null`**：从旧站迁入的老帖只有 `editTime`，代码用它兜底，
  否则日期会落成 1970。
- **约 20% 是打卡动态**（`content` 为空），约 70% 是题解/内推广告/闲聊，
  真正的面经大约只占 **10%**。所以噪声闸门有四道，见 README「噪声闸门」。

### 数据流

```
牛客 API ──scrape──▶ posts（原始帖子）
牛客 sitemap ──fetch──▶ data/raw/*.html.gz ──parse──▶ posts
                                  │
                             importer（清洗/分类/聚类）
                                  ▼
                        questions ◀── occurrences ──▶ posts
                      （去重后的问题）  （出现记录，带原文链接）
```

抓取与解析分离的理由见「全站面经抓取」一节：原始数据只抓一次，判据可以改无数次。

**`occurrences` 是这套设计的核心**：它同时连接「问题」和「帖子」，并携带该帖中的原始措辞。
所以每个问题都能回答「谁在什么时候、哪场面试里问的」，并直接给出**原文链接**。

## 数据库设计

MySQL 8.0 / InnoDB / `utf8mb4_unicode_ci`（题干含中文与 emoji）。DDL 见 `internal/store/migrations/001_init.sql`。

| 表 | 作用 |
|---|---|
| `posts` | 原始帖子：标题、正文、公司、岗位、轮次、**原文 URL** |
| `questions` | 去重后的问题：代表措辞、归一化键 `norm`(UNIQUE)、模块、主题、出现次数 `n` |
| `question_variants` | 同一问题的其他措辞 |
| `occurrences` | 问题 × 帖子的出现记录（`UNIQUE(question_id, post_id)`），含该帖里的原始措辞 |
| `schema_migrations` | migration 追踪（`ALTER TABLE` 不幂等，必须有） |

三层结构的好处：**频次可以在任意筛选条件下重算**。
例如「一面 + Agent/AI 模块」下 `n` 只统计符合条件的出现记录，而不是全库计数。

### 迁移到 MySQL 时踩到的几个点

从 SQLite 迁过来不是改个 driver 就行，这几处必须处理：

1. **`ON CONFLICT ... DO UPDATE` → `ON DUPLICATE KEY UPDATE`**，并且用了 MySQL 8.0.19+ 的
   行别名语法（`VALUES (...) AS new`）而不是已废弃的 `VALUES(col)` 函数。
2. **`TRUNCATE` 需要临时关闭外键检查**——被外键引用的表无法直接 TRUNCATE（MySQL 看的是
   约束是否存在，而非有无数据）。而 `SET FOREIGN_KEY_CHECKS` 是**会话级**的，用连接池会飘到
   别的连接上，所以整个清空序列必须跑在 `db.Conn()` 取出的**同一条连接**上。
3. **`SUM()` 返回 DECIMAL**，扫进 Go 的 `int` 会出问题，统一 `CAST(... AS SIGNED)`。
4. **`LENGTH()` 在 MySQL 里数的是字节**，中文会算成 3 倍。排序用 `CHAR_LENGTH()`。
5. **`ONLY_FULL_GROUP_BY`**（MySQL 8 默认开启）：因为 `q.id` 是主键，其余列函数依赖于它，
   所以 `GROUP BY q.id` 同时选 `q.canonical` 是合法的——但这点依赖 MySQL 的函数依赖推导。
6. **`DATE` 类型**：`posted_date` 用 `DATE` 存，读取时用 `DATE_FORMAT(...,'%Y-%m-%d')`
   显式转成字符串，避免驱动 `parseTime` 带来的时区换算。
7. **DDL 不能进事务**（隐式提交），所以 `TRUNCATE` 在事务外，插入仍在事务内。
8. **不启用 `multiStatements`**（会放大注入面）：migration 文件在 Go 侧切分后逐条执行。

SQL 全部收在 `internal/store` 内，上层不感知数据库；换回 SQLite 或迁 PostgreSQL 只需重写该包与 migrations。

## 前端

原生 JS，无构建步骤。五个视图：

- **概览** — 统计卡 + 主题/轮次/岗位/公司分布 + TOP 20 高频题（主题分布已排除「开场/通用」）
- **按轮次** — 一面 / 二面 / 三面及以上 / HR 面 / 复活赛
- **按岗位** — Agent 开发 / 全栈开发 / 平台·Infra / 数据平台 / AI·算法 / Go / C++ / 其他
- **按公司** — 全部 66 家
- **按模块** — 后端工程 / Agent·AI / 项目 / HR·软性 / 算法 / 计算机基础 / 开场·通用，
  **并可按主题二级筛选**（主题列表只显示该模块下真实存在的主题，避免点到必然为空）

筛选状态同步到 URL hash，可直接分享：

```
http://127.0.0.1:8787/#module?category=Agent%2FAI&topic=MCP%20%2F%20Skill
```

每个问题点击展开：其他措辞 + 被问到的场合，每条场合带 **「原文 ↗」** 链接（新标签打开牛客原帖）。

### 踩过的三个前端坑

**① `d.items.map(qCard)` 会静默传错参数。** `Array.map` 会把 `(元素, 下标, 数组)` 三个实参
都传给回调，所以 `qCard(q, 0, arr)` 里的 `open` 收到了**下标**——结果是「除第一项外全部默认展开」。
必须写成 `map((q) => qCard(q))`。

**② 拼 HTML 字符串不会绑定事件。** 早先版本用 `innerHTML = items.map(qCard).join('')` 生成列表，
却仍按「先建 DOM 再逐个绑 onclick」的思路写，结果是**点击完全没有反应**；
再叠加 ①，视觉上就表现为「第一题点不开、其他题默认展开」。

现在统一用**事件委托**：容器上绑一次 `onclick`，靠 `closest('.qh')` 找触发元素。

**③ 改 Go 的 JSON tag 会让「原文 ↗」链接静默消失。** 加 LLM 字段时顺手把
`Question.Occurs` 的 tag 从 `occurrences` 写成了 `occurs`，而前端读的是 `q.occurrences`——
`(q.occurrences || [])` 的兜底把它变成空数组：**链接全没了、控制台无报错、接口还返回 200**。
这类前后端隐式契约靠人眼极难发现，所以加了 `internal/model/model_test.go`
用测试钉住字段名（含反向断言：旧名 `occurs` 不得复活），并验证过「改错就会红」。

> 教训：前端里的 `x || []`、`x ?? []` 兜底会吞掉**契约变更**这类错误。
> 对跨端字段名，宁可让测试兜住，也不要让运行时的默认值兜住。

## 标题字段：宽松解析

`ParseTitle` 只认「公司 岗位 轮次」严格格式，那是**一个用户**的写作习惯。全站标题多为自由写法，
于是 `company` 大面积为空、整个「按公司筛选」维度近乎失效（sitemap 帖 198 篇只有 11 篇解析出公司）。

`internal/scraper/title.go` 补了一条宽松路径：严格格式 → **词典最长匹配** → 「轮次词之前那段」启发式。
实测公司覆盖率 **3.6% → 77%**，公司数 **73 → 167**。

- 词典会自己长大：`cmd/parse` 把库里已有的公司名喂进来，所以一家公司在任何标准格式标题里出现过，
  之后出现在自由标题里也能被认出
- **精度优先**：单字不算公司名；只在标题里确实有轮次词时才「猜」；候选含句点逗号疑问句尾助词就放弃
- **回填自愈**：对全部帖子重算而不是只补空字段，这样解析规则修好后旧的错误值也会被纠正

踩过的两个坑都有回归测试：`TA\b` 把 `momenTA` 认成「技术美术」（Go 的 `\b` 是 ASCII 语义）；
一个单字「招」混进词典后 `strings.Contains` 让所有含「招」的标题（秋招/校招/招聘）被认成同一家公司、79 篇错帖。

### 页签一览

概览 / 按知识点 / 按轮次 / 按岗位 / 按公司 / 按模块 / **公司×知识点** / **复习清单** / 面经原文。

- **全局时间栏**在页签下方：预设（全部 / 近 7 天 / 近 30 天 / 近 90 天）+ 起止日期。
  它限定**下面展示的全部内容**——统计卡、各维度计数、矩阵、题目与原文列表，
  并跨页签保留、写进 URL hash。⚠️ 按发布时间筛，受 sitemap 限制目前只有
  2024-11 与 2026-08/09 三个月份有数据。
- **搜索框**在列表页顶部，按代表措辞与**全部变体**匹配（例如搜 `LRU` 能命中
  「手撕：lru」这类写法），输入即筛选，状态同步进 URL hash 可分享。
- **公司×知识点**把两个维度交叉成热力矩阵，单元格是去重后的题目组数。
  点格子直接跳到该组合的问题列表。
- **复习清单**按复习优先级排序（公司覆盖面 × 3 + 频次上限 20 + 有答案加 4），
  并带打印样式——这个视图的实际用法就是打印出来当提纲。

### 轮次兜底：只认正文里的「标题式行」

标题能给轮次的只有约一半，剩下的从正文兜底。但**正文里不能任意位置搜轮次词**——
实测那样会把《嵌入式CAN总线必备八股文总结》整篇 40 道通用八股标成「一面」，
只因为正文里有一句叙述「一面却卡在第一层」。

所以规则是：整行 ≤24 字且以轮次词开头的「标题式行」才算，且按**轮次键**归一
（`一面`/`第一轮`=1、`二面`=2、`三面`=3、`终面`=5、`HR面`=hr）；
出现两种以上键（帖子横跨多轮）就**留空**——错标比不标更糟，用户按轮次筛会筛出错的东西。

同一批数据：宽松版 129 篇 / 1,544 题 → 收紧版 **20 篇 / 279 题**。
详见 `docs/RETROSPECTIVE.md` 问题 11。

## 抓取实现要点

这几条都是实测结论，踩过坑的记录：

1. **列表接口在 `gw-c.nowcoder.com`**，不是 `www`；参数是 `pageNo`，不是 `page`。
   拼错主机或参数名会返回 SPA 的 HTML 外壳（HTTP 200 但不是 JSON），非常容易误判。

2. **列表响应里就带完整正文**（`records[].momentData.content`），无需逐篇抓详情页。
   8 页覆盖近半年，成本极低。

3. **原文链接必须用 `moment.uuid`**：
   `https://www.nowcoder.com/feed/main/detail/<uuid>` ✅
   用 `contentId`（如 `2906657`）会落到客户端渲染的空壳，`/discuss/<uuid>` 直接 404。

4. **分页终止条件用时间而非页数**：抓到最早一条越过截止时间即停。
   注意 API 尾部会追加几条历史帖（旧帖混在 `2026-07-29` 之后），不能只看单条判断。

5. **礼貌抓取**：默认 1.2s/页间隔，遵守 robots.txt（该站仅禁 `/search`、`/nccommon`、`/ab/`）。

### 全站抓取（`cmd/fetch`）实测结论

6. **sitemap 是全站入口**：`sitemap1.txt` + `sitemap2.txt` 共 26,623 条，
   `/feed/main/detail/<uuid>`（16,163）与 `/discuss/<数字ID>`（9,856）结构完全一致，
   都走 `prefetchData.2.ssrCommonData.contentData`，**免登录**，不需要写两套解析。

7. **空壳页是最大的坑**：站点软限流时返回约 6KB 的骨架 HTML（无 `contentData`），
   但 HTTP 状态是 **200**。不识别的话会把空壳当成功结果永久落盘，
   而且 `Has()` 判重会让这个 URL **再也不会被重抓**。
   判据 `LooksLikeContentPage` 只检查正文是否含 `contentData`；不含就按可重试失败处理。
   实测：固定 0.5s 连发时约 2/3 的请求是空壳，改成随机 1.5~4s 后降到 0。

8. **`createdAt` 对老帖是 `null`**：`/discuss/<数字ID>` 那批（旧站迁入）只有 `editTime`。
   用它兜底——`editTime` 只会偏晚不会偏早，对「近 N 个月」过滤是可接受的近似。

9. **`-shuffle` 不是可选优化**：sitemap 顺序固定，不洗牌的话每次重跑都从同一段前缀开始，
   在站点看来就是「同一个爬虫反复扫同一段」。洗牌后每轮从队列随机位置开始。

10. **抓取成本 ≫ 入库成本**：26,623 份 HTML 最终只有约 10% 能变成面经。
    这正是「落盘优先」的意义——原石留着，判据改了不用重抓。

## 噪声闸门

抓全站会发现，**「像面经」和「是面经」差了十倍**。四道闸门，前两道便宜（抓取侧），后两道精确（入库侧）：

| 闸门 | 位置 | 判据 |
|---|---|---|
| ① 空内容 | `LooksLikeInterview` | 标题与正文都为空——约 20% 是**打卡动态**（`clockMoment` 有值、`circle` 是打卡圈），不是抓丢了 |
| ② 题解/广告 | `IsRecruitAd` | 有强广告词**且**面试信号 < 2 处 |
| ③ 非问题行 | `IsQuestion` | 进展描述、面后感、整行括号、算法行备注 |
| ④ 零题目帖子 | `PruneEmptyPosts` | 一条题都抽不出来 → 整帖删除 |
| ⑤ 模型判定 | LLM 归类 | 最终权威：判为「非题目」的默认不展示 |
| ⑥ 转帖刷频次 | `DeduplicatePosts` | 归一化标题相同 **且** 题集 Jaccard ≥ 0.8 → 只保留最早一篇 |

③ 里有一批规则不是拍脑袋写的，而是**拿模型标注反推**出来的：用 2466 条「模型判定为非题目」
和 3863 条「有效题」当标注集，逐条算精确率，**只采用精确率 ≥94% 的**
（内推广告 98.7%、面试指导语 100%、话题标签行 94.8%）。
看着更有效的「长句且无问号」只有 78.7%、「含建议词」只有 50%，就没采用——
这类"看起来有效"的规则正是凭直觉写规则时最容易犯的错。详见 `docs/DEPLOYMENT.md` 5.5。

**② 为什么是「对比」不是「命中」**：内推广告的标题常带「秋招/校招」会命中面经关键词；
内容又常写成「投递方式：1. 2. 3.」加「项目经历」等备赛建议——
**单看任何一侧都会误判**（这两种误判都真实发生过）。
所以判据是「广告信号 vs 面试信号」的数量对比。真面经偶尔结尾也挂内推码，
但那种帖子面试信号必然远多于 2 处，不会被误杀。

**最高质量的题源：官方结构化真题。** 牛客有 4.3% 的内容页带
`experienceQuestionList`——发帖人/官方把题目整理成了 `{题目, 参考答案}` 列表，
平均每帖 **11.1 条**，**100% 带答案**。按全站推算约 1.2 万条带答案的题。
它比正文正则抽取的产出率高、且干净得多，所以现在是一条独立管线
（`posts.official_q` → `importer.officialRows` → `questions.answer`），
前端有「只看有答案」「只看官方真题」两个开关。详见 `docs/DEPLOYMENT.md` 5.4。

**④ 为什么需要它**：粗筛靠关键词，总会漏掉「恐怖的秋招」「笔试题求经验」这类
看着像、其实没题目的帖子。而「一个题目都抽不出来」是**数据自己给出的结论**，
比任何关键词都准。代价是必须先入库再删，所以放在 `ReplaceQuestions` 之后
（那时 `occurrences` 才是最新的）。

> ⚠️ **杀噪声之前必须先确认召回。** 「数据为空」有两个来源：帖子是噪声，
> 或者抽取漏了。两者在库里长得**完全一样**（都是 0 条出现记录）。
>
> 本项目真踩过：`Extract` 早先用 `p.Company == ""` 判断「不是面试帖」，
> 而 `company` 来自「公司 岗位 轮次」这个严格格式。于是
> 「上海某量化开发 一面」（只有一个空格）、「遥望科技 hr面」「转转 FDE 线下面试」
> 这批真面经被整篇跳过。若当时直接跑清理，删掉的就是真数据。
>
> 换成「标题里有没有面试信号」后，问题 1478 → **1576** 组，
> 真正空的帖子从 13 篇降到 **4 篇**。回归测试：
> `TestExtractDoesNotDropTitledInterviews`。

**⑥ 为什么要有「转帖」这道闸门。** 内推广告会把**同一份模板面经题单**连同自己的
内推码复制几十上百遍。这些转帖不是几十个人真的考过同一道题，但按出现次数统计，
模板里每道题都会被刷成 57×、76× 这种**整齐的假频次**——而本站的核心功能就是按频次排序。

两个关键点：

- **广告规则在这里天然失效**：`IsRecruitAd` 要求「面试信号 < 2」，可这类广告
  *自己带着一整份题单*，题单里的「一面 / 自我介绍 / 手撕」直接把信号刷满。
  而且 178 篇这类帖子贡献了 22% 的有效题记录，当广告删掉会连题一起删。
- **问题在重复计数，不在内容**：所以判据是「同归一化标题 **且** 题集 Jaccard ≥ 0.8」，
  只留最早一篇。实测删掉 409 篇（19%），**有效题一道没少**，
  Top 榜从「76× ×4、57× ×22」变回真实分布（19×、15×、13×…）。
  该闸门**幂等收敛**：再跑一次命中 0 篇。

> 判据里必须带「题集」这一条：只看标题会误杀——两个不同的人写《字节一面面经》
> 是正常的，题集不重合就不该删。测试：`TestDuplicatePostIDsKeepsDifferentContentSameTitle`。
> 详见 `docs/DEPLOYMENT.md` 5.7。

## 分类体系

**同时存在两套分类，是刻意的**：规则分类快而稳、可解释；模型分类准而细、能捕捉语义。
两者并存互为参照，页面上按视图切换标签来源。

### 第一套：规则分类（7 个模块 + 主题）

由正则优先级判定，`internal/importer/importer.go`。适合快速迭代与离线重建（`make rebuild`）。

### 模块（7 个）

设计取向：**把「项目经历」与「知识点」彻底分开**，并把原本笼统的「八股」按考察对象
拆成「计算机基础（四大件）」与「后端工程」——前者是 OS/网络原理，后者是语言/存储/中间件/容器/架构/性能。

| 模块 | 承载什么 | 判定要点 |
|---|---|---|
| `算法` | 手撕/写代码 | `手撕`/`手写` 开头，或命中具体题名（LRU、接雨水…） |
| `计算机基础` | 操作系统 + 计算机网络 | 进程/线程/协程/死锁/内存；TCP/HTTP/DNS/握手 |
| `后端工程` | 语言/存储/中间件/容器/架构/性能/工程实践/前端 | 含语言或框架线索（Go、MySQL、Redis、K8s…） |
| `Agent/AI` | Agent 架构、MCP/Skill、上下文、RAG、LLM、AI 编码 | |
| `项目` | 项目经历深挖 | 「你的项目」「你们这套」「重构」「AB 测试」 |
| `开场/通用` | 流程套话：自我介绍、团队介绍、反问 | **不计入知识点统计** |
| `HR/软性` | 离职/薪资/绩效/规划 | |

判定顺序即优先级。两处顺序是刻意的：

- **`开场/通用` 必须排在 `项目` 之前**——否则「先简单介绍一下你做的事情」会被项目规则抢走。
- **`后端工程` 排在 `计算机基础` 之前**——「Go 的协程调度」属于 Go 语言（后端工程/语言特性），
  而「进程、线程、协程的区别」不含语言线索，自然落到计算机基础/操作系统。

### 主题（二级，按模块分组匹配）

主题规则**按模块分成不同的集合**，不是一套规则通吃。
否则「Go 的协程调度」会因为含「协程」而被归到「操作系统」主题——模块与主题自相矛盾。

### 复合题拆分

原始帖里一行可能塞了多道题：

```
手撕：大数相加 & 接雨水          →  手撕：大数相加 / 手撕：接雨水
手撕：判断链表有环 & 树的层序遍历   →  手撕：判断链表有环 / 手撕：树的层序遍历
```

**只对算法行生效**。其他题型里的 `&` 和 `、` 通常是同一道题的并列成分——
「上下文管理、Skill 和 MCP 的理解」是一道题，拆了反而错。

### 聚类

- 归一化保留英文数字——`DNS`/`gRPC`/`Go` 才是技术题的主体，去掉会让不同题撞车。
- 相似度用 Levenshtein，阈值 0.82；另加「包含关系」判定。
- 改了规则后**不必重抓**：`make rebuild` 会用库内帖子正文重建。

> **关于「高频」的一个诚实说明**：面试题多为项目相关、措辞各异，字面重复率很低
> （1525 条 → 1493 组，最高频仅 4 次；「其他技术」类 410 组全部是 n=1 的长尾）。
> 所以真正的「高频」信号要看**主题级**——例如「Go 协程」被多家公司以不同措辞问到，
> 按字面去重会完全漏掉。

### 测试

分类与拆分规则有单元测试锁定（`internal/importer/classify_test.go`），覆盖：
复合题拆分、7 个模块的判定边界、备注/吐槽剔除、知识点与非知识点的区分。

这些测试在开发中抓出了两个真实 bug：
1. `SplitCompound` 里 `reAlgoLead` 把尾部的 `：` 也吃进 prefix，又拼一次 → `手撕：：`
2. `reMetaRemark` 把**任何以「面试官」开头**的内容都当备注，误杀「面试官问的那道 LRU 你还记得吗？」

### 第二套：LLM 分类（三层：合并类 → 顶层域 → 细分类）

现状：**68 个细分类 / 33 个可用类 / 7 个顶层域**，覆盖全部 3038 组问题。
其中 489 条（16%）被判定为「非题目」——**模型判噪比规则准得多**，
默认列表不显示这些条目（有「显示非题目」开关）。

跑法：

```bash
make llm-sample    # ① 分层抽样 → data/llm/sample.json
                   #    让模型据此产出 data/llm/taxonomy.json
make llm-batches   # ② 分批（150 条/批）→ data/llm/batches/
                   #    子代理逐批归类 → data/llm/out/batch-NN.json（每条必带 text）
make llm-apply     # ③ 应用（写 llm_labels + 物化到 questions）
make llm-stats     #    看看各细分类条数，决定怎么合并
```

编辑 `data/llm/merge.json` 后重跑 `make llm-apply` 即可换一种合并方式，**不需要再调模型**。

规则分类的死穴是「同一个考点换个说法就散了」——比如「Go 的协程调度」和「GMP 模型」字面
相似度低，规则很难归到一起，而语义上是同一件事。所以引入模型归类。

**流程分三步，刻意解耦：**

| 步骤 | 产物 | 说明 |
|---|---|---|
| ① 探索 | `data/llm/taxonomy.json` | 先从分层抽样里让模型**尽可能细**地提出分类体系（本次 **50 个**细分类），再按域归组 |
| ② 归类 | `data/llm/out/batch-*.json` | 分批（150 条/批）并行归类，每批一个子代理：读批次文件、写结果文件，数据不经过主上下文 |
| ③ 合并 | `data/llm/merge.json` | 人看过各细分类的条数后，决定哪些合并成**可用的 26 个类** |

**为什么三步分开**：合并规则变了只需重跑第 ③ 步（`make llm-apply`），**不必再调模型**。
三层都留在库里（`llm_merged` / `llm_domain` / `llm_cat`），随时可以换一种合并方式。

**探索阶段暴露的体系缺口**（代理主动反馈，非常有价值）：
- 没有**数据库 / SQL** 类 → `MySQL 索引`、`Text to SQL` 无处可归
- 没有**前端客户端**类 → `vue 双向绑定` 无处可归
- 没有**大模型训练原理**类 → `Transformer 思路`、`模型怎么训练的` 无处可归
- 没有**内容安全**类

合并时补了这 5 个缺类（`数据库与 SQL`、`前端与客户端`、`大模型训练与原理`、`算法工程化`、`数据结构基础`），
并把 12 条「其他」手工归位。

**模型分类的一个附带收益**：它标出了 **40 条「非题目」**——比我正则能覆盖的多得多。
例如 `30min搞完，感觉可能会是kpi面`、`流水提交下（学历、学位、个税、背调）`、
`双机位面试确实有点难绷` 这类进展记录/吐槽，正则很难穷举，语义判断却很稳。

**重建不会丢标注**：`ReplaceQuestions` 在 TRUNCATE 前按 `norm` 暂存 LLM 归类，插入后还原。
改一条规则分类不必重跑模型（实测 1477 条标注全部保留）。

### 分类效果对比

| 维度 | 规则分类 | LLM 分类 |
|---|---|---|
| 粒度 | 7 模块 / 23 主题 | 50 细分类 → 26 可用类 / 6 域 |
| 典型误判 | 「Go 的协程调度」模块对、主题串到「操作系统」 | 语义一致，且能区分「Go 协程」与「进程线程协程」 |
| 非题目识别 | 正则穷举，40 条里能盖住 ~26 条 | 语义判断，覆盖 40 条 |
| 成本 | 毫秒级、离线可重跑 | 需调模型（本次 11 个子代理、约 1500 条） |

两套都在库里，页面上「按知识点」用模型分类，「按模块」用规则分类。

## 合规与边界

- 只抓取**公开**内容；robots.txt 允许的范围内（该站仅禁 `/search`、`/nccommon`、`/ab/`）。
- 全站抓取走牛客**主动发布**的 sitemap，单线程、随机 1.5~4s、每 30 条长休息，
  并对软限流自动退避——站点要求慢下来时我们会慢下来。
- 内容为 UGC，版权属发帖人；请勿再分发或商用。
- Cookie 仅从环境变量注入，**不写入任何文件**（见 `.gitignore`）。
- 服务默认只绑 `127.0.0.1`，**无鉴权**；对外暴露前必须加认证。
